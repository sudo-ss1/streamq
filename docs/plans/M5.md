# M5 — Metadata Raft (plan)

SPEC refs: §2.1 (every broker a Raft voter, static membership, BootstrapCluster with the identical
server list ignoring ErrCantBootstrap, controller = Raft leader, FSM contents, change notifier,
snapshots, versioned deterministic commands), §2.2 (`metadata/raftstore`), §2.3 (liveness:
heartbeat every 2 s, fence after 9 s, fencing removes from ISRs and re-elects leaders, re-register
and unfence once caught up), §4.4 (election rule: first live ISR member in replica order, epoch++,
unclean disabled), §7.2 (RegisterBroker, BrokerHeartbeat), §7.3 NOT_CONTROLLER, §9 M5.
Acceptance (§9): in-process 3-broker test — a topic created via any broker is visible everywhere;
controller killed → a new controller is elected and metadata is intact; FSM snapshot/restore
round-trip test.

Out of scope: data replication / follower fetching / AlterISR / acks=all purgatory (M6), producer
id blocks (M7), controlled shutdown (M8). In M5 a partition whose leader is on another broker is
served as NOT_LEADER (with the leader hint); RF>1 topics can be created and their metadata is
correct, but follower data does not flow until M6.

New dependencies (approved list): `github.com/hashicorp/raft`, `github.com/hashicorp/raft-boltdb/v2`.

## 1. FSM additions (`internal/metadata`, main session)

`State` gains `Brokers []Broker` becoming the **registered** brokers:
`Broker{ID, Host, Port (client), InternalAddr, Fenced bool, Epoch int64 (registration count)}`.
New versioned commands (`internal.proto`, additive oneof fields 13–15):
- `RegisterBrokerCommand{broker_id, host, port, internal_addr}` — adds or updates the broker,
  `epoch++`, and leaves it **fenced** (it is unfenced once caught up, §3).
- `FenceBrokerCommand{broker_id}` — marks fenced; for every partition: remove the broker from the
  ISR **unless it is the only ISR member** (Kafka keeps the last member so unclean election stays
  impossible); if it was the leader, elect: first replica in replica order that is in the (new) ISR
  and unfenced; if none, leader = −1 (offline, NOT_LEADER until an ISR member returns). Any leader
  change or ISR change bumps `leader_epoch` (leader change only) and `partition_epoch` (any change).
- `UnfenceBrokerCommand{broker_id}` — marks unfenced; every **offline** partition (leader −1) whose
  ISR contains the broker elects it (replica order among unfenced ISR members), epoch++.
- `CreateTopic` assignment uses **unfenced registered** brokers (RF ≤ that count, FR1); initial
  leader = first replica, ISR = replicas.
All deterministic (no clock reads; the controller passes timestamps). Changes emitted:
`PartitionChanged` (with the new `PartitionState`s) and `BrokersChanged`.

The controller is **not** part of FSM state (it is the Raft leader); `Snapshot.ControllerID` is
filled by the store from Raft's current leader.

## 2. `metadata/raftstore` (main session)

```go
type Config struct { NodeID int32; RaftAddr string; Peers []Peer /* id, raft addr, internal addr */;
    DataDir string; Logger *slog.Logger; HeartbeatTimeout, ElectionTimeout, CommitTimeout,
    LeaderLeaseTimeout time.Duration (zero = defaults; tests use small values);
    SnapshotThreshold uint64; SnapshotInterval time.Duration; Forwarder Forwarder }
type Forwarder interface { // implemented by the internal gRPC client (§4)
    Forward(ctx, leaderInternalAddr string, cmd *streamqv1.MetadataCommand) error }
func Open(ctx, cfg Config) (*Store, error)   // raft-boltdb log+stable store in <data_dir>/raft/,
    // file snapshot store (retain 2), TCP transport on RaftAddr; BootstrapCluster(all peers),
    // ignoring raft.ErrCantBootstrap
func (s *Store) Snapshot() metadata.Snapshot     // FSM state + ControllerID from raft.Leader()
func (s *Store) Propose(ctx, cmd) error           // leader: raft.Apply (marshalled proto),
    // wait for the future, return Apply's error; follower: Forward to the leader's internal
    // address; no leader known → retry with backoff until ctx; forwarded command rejected because
    // the target lost leadership → retry (bounded by ctx), finally metadata.ErrNotController
func (s *Store) ApplyLocal(ctx, cmd) error        // leader-only path used by the internal RPC
    // handler for forwarded commands (returns ErrNotController if not leader — no re-forwarding)
func (s *Store) Subscribe(fn) (Snapshot, func())  // same contract as local.Store
func (s *Store) IsLeader() bool; LeaderID() int32; LeaderCh() <-chan bool  // controller hooks
func (s *Store) AppliedIndex() uint64; CommitIndex() uint64  // catch-up checks (§3)
func (s *Store) Close() error                     // raft.Shutdown, stop notifier, close bolt
```
FSM (`raftstore/fsm.go`): `Apply(*raft.Log)` unmarshals `MetadataCommand`, calls
`State.Apply`; command errors are returned as the `ApplyFuture` response (deterministic: every node
gets the same error and the state is unchanged); successful changes are queued for subscribers
(the same notifier design as `local.Store`: copy → apply → swap under the FSM mutex; one owned
notifier goroutine). `Snapshot()` returns a `raft.FSMSnapshot` holding a deep-copied `State`
marshalled to JSON in `Persist`; `Restore` replaces the state and emits a `Restored` change so
subscribers resync (the broker re-applies the full snapshot idempotently). Raft's logger is
adapted to slog (hclog adapter in-package).

The local store (M2–M4) stays for single-node mode: `node.Start` uses raftstore when `cluster` is
non-empty, else local (no migration between them; D30).

## 3. Controller (`internal/controller`) — liveness and fencing

Runs on every broker; active only while the local Raft node is leader (watches `LeaderCh`).
```go
type Proposer interface { Propose(ctx, *streamqv1.MetadataCommand) error;
    Snapshot() metadata.Snapshot; CommitIndex() uint64 }
type Clock interface { Now() time.Time; NewTicker(d) (C <-chan time.Time, stop func()) }
type Controller struct { ... }
func New(cfg Config{BrokerID; SessionTimeout (9s); CheckInterval (1s)}, p Proposer, clock, logger) *Controller
func (c *Controller) Register(ctx, req) (RegisterResult{BrokerEpoch, CatchUpIndex}, error)
    // leader only (else ErrNotController with leader hint): propose RegisterBroker; remember
    // lastHeartbeat=now and catchUpIndex = CommitIndex() after the propose
func (c *Controller) Heartbeat(ctx, brokerID, brokerEpoch, appliedIndex) (fenced bool, err)
    // leader only; stale epoch → error (broker must re-register); record lastHeartbeat; if fenced
    // and appliedIndex >= catchUpIndex → propose UnfenceBroker
func (c *Controller) Run(ctx) error  // ticker: while leader, fence brokers whose lastHeartbeat is
    // older than SessionTimeout (propose FenceBroker once per expiry); on gaining leadership,
    // initialise lastHeartbeat=now for every registered broker (grace period, Kafka-like)
```
In-memory state guarded by one mutex; Propose never called under it.

## 4. Internal RPC (`api/v1/internal.proto`, new service; `internal/server/internal.go`)
```proto
service StreamQInternalService {
  rpc RegisterBroker(RegisterBrokerRequest) returns (RegisterBrokerResponse);
  rpc BrokerHeartbeat(BrokerHeartbeatRequest) returns (BrokerHeartbeatResponse);
  rpc ForwardMetadata(ForwardMetadataRequest) returns (ForwardMetadataResponse); // follower→leader
}
message RegisterBrokerRequest { int32 broker_id = 1; string host = 2; int32 port = 3; string internal_addr = 4; }
message RegisterBrokerResponse { ErrorCode error_code = 1; string error_message = 2; int64 broker_epoch = 3; int32 controller_id = 4; }
message BrokerHeartbeatRequest { int32 broker_id = 1; int64 broker_epoch = 2; uint64 applied_index = 3; }
message BrokerHeartbeatResponse { ErrorCode error_code = 1; string error_message = 2; bool fenced = 3; int32 controller_id = 4; }
message ForwardMetadataRequest { MetadataCommand command = 1; }
message ForwardMetadataResponse { ErrorCode error_code = 1; string error_message = 2; int32 controller_id = 3; }
```
The internal service listens on `internal_addr` (separate gRPC server, D31). Errors from a
forwarded `State.Apply` map to the usual codes and back to the same sentinels on the follower
(a small code→sentinel table in raftstore's forwarder).

Broker side (`internal/node` + a `liveness` loop in `internal/broker` or node): on start, register
with the controller (retry/backoff, following `controller_id` hints), then heartbeat every
`broker_heartbeat_interval_ms` with the store's applied index; on "stale epoch"/unknown → re-register.

## 5. Public API changes (additive)
- `CreateTopicResponse`/`DeleteTopicResponse` gain `int32 controller_id = 3` (the NOT_CONTROLLER
  hint, SPEC §9 "forwarding hints"); with server-side forwarding (§2 Propose) clients rarely see
  NOT_CONTROLLER (only when no leader exists within the request deadline).
- `MetadataResponse.brokers` lists **unfenced** registered brokers; `controller_id` = Raft leader.
- Group coordinator: `FindCoordinator` returns the controller's broker; non-controllers answer group
  RPCs with NOT_COORDINATOR (existing R11 check now meaningful). On controller change the old
  coordinator's in-memory groups are cleared (members get UNKNOWN_MEMBER_ID and rejoin, SPEC §5).
- Client (`pkg/client`): Admin retries NOT_CONTROLLER with backoff after a metadata refresh;
  GroupConsumer already rediscovers on NOT_COORDINATOR.

## 6. Broker reactions (main session)
`internal/broker` handles `PartitionChanged`: if the local broker becomes leader → `BecomeLeader`
(epoch from metadata); if it is now a follower → `BecomeFollower(leader, epoch)` (M5: marks not
leader so requests get NOT_LEADER with the leader hint; M6 starts the fetcher). `Restored` change
→ resync all partitions from the snapshot idempotently. Partitions for which the local broker is
a replica are opened (logs created) on every replica, not only the leader.

## 7. Config & node
`cluster` non-empty ⇒ Raft mode: validates every member has raft/internal/client addrs, local
`broker_id` present (existing validation). New optional keys for tests/tuning: `raft_heartbeat_timeout_ms`
(default 1000), `raft_election_timeout_ms` (1000), `raft_snapshot_threshold` (8192) — additive
(D32). `node.Start`: open raftstore (internal gRPC server started first so forwarding works),
controller, broker, coordinator, public server; shutdown order reversed; liveness loop owned by
node.

## 8. Tests
- **FSM** (`internal/metadata`): register/fence/unfence tables: ISR shrink except last member,
  leader election in replica order skipping fenced, offline partition (leader −1) when no ISR
  member alive, unfence re-elects offline partitions, epochs bump exactly when leader/ISR change;
  CreateTopic uses unfenced brokers only; determinism (apply the same command list to two states →
  equal JSON).
- **raftstore**: FSM `Snapshot().Persist` → `Restore` round trip equals the original state (§9
  criterion) incl. groups; command errors are deterministic and leave state unchanged on all
  nodes; 3 nodes on 127.0.0.1 with fast timeouts: elect a leader, propose on a follower (forwarded),
  converge on all; subscribers on every node see the change once; leader shutdown → new leader,
  state intact, proposals continue; restart a node from its data dir (bolt + snapshot) and it
  catches up; snapshot taken (low threshold) and log truncated, restart restores from snapshot.
- **controller**: fake clock + fake Proposer: register → fenced until heartbeat reports
  applied ≥ catch-up index → UnfenceBroker; missing heartbeats beyond SessionTimeout → exactly one
  FenceBroker; leadership gained → grace period (no immediate fencing); not leader →
  ErrNotController.
- **server**: internal RPC handlers mapping; NOT_CONTROLLER hint fields.
- **Integration (§9)** `test/integration/cluster_test.go`: 3 in-process nodes (ports pre-allocated
  on 127.0.0.1): wait for a controller; create a topic (RF 3) via each of the 3 brokers (3 topics);
  all 3 visible with identical partition metadata in every broker's `Metadata` (require.Eventually);
  close the controller node → a new controller elected among the remaining two
  (`controller_id` changes, within ~10 s), all topics intact, a further CreateTopic via a survivor
  works; the killed node restarts on its data dir, re-registers, gets unfenced, and sees all
  topics; fencing: after the killed node was down > session timeout, partitions it led have a new
  leader with a bumped epoch (FR election rule observable via Metadata).

## 9. Parallel split
The FSM, raftstore and broker reactions are correctness-critical and coupled (CLAUDE.md: "the M5
FSM … built by the main session alone"). One implementer package:

| pkg | owner | owned paths | contract | done |
|---|---|---|---|---|
| A controller | implementer | `internal/controller/**` | `Proposer`, `Clock`, commands in internal.proto, `metadata` broker fields — committed first | §8 controller tests |
| B everything else | main | metadata FSM, raftstore, internal RPC, broker reactions, node, client tweaks, integration | — | §8 rest |

## 10. Decisions
- D30 Single-node mode keeps the local JSON store; cluster mode uses raftstore; no migration.
- D31 Broker-to-broker RPCs use a separate gRPC service on `internal_addr`.
- D32 Raft timing knobs as optional config keys (defaults tuned for a laptop cluster: heartbeat /
  election 1 s, so failover happens within a few seconds).
- D33 Server-side forwarding of metadata proposals from followers to the controller (Kafka
  KIP-590-like); NOT_CONTROLLER (+ controller_id hint) only when no controller is reachable in time.
- D34 Fencing keeps the last ISR member in the ISR (no unclean election); offline partitions are
  re-elected when an ISR member is unfenced.
- D35 Registration leaves a broker fenced until its heartbeat reports a metadata applied index ≥
  the controller's commit index at registration ("caught up", SPEC §2.3).

## Revision 1 (after plan-review round 1)

These rules supersede anything above that conflicts with them. **M5 is built sequentially by the
main session** (finding 8): there is no implementer split.

- **R1 (BLOCKER 1) Catch-up before the broker opens**:
  - Cluster-mode `node.Start` does, in order:
    1. bind listeners;
    2. open raftstore and the internal gRPC server;
    3. start the controller (inactive until leader);
    4. register with the controller (retrying and following hints);
    5. wait until the broker-side processed index is ≥ the `catch_up_index` returned in
       `RegisterBrokerResponse` (new field 5);
    6. only then call `broker.Open`;
    7. start the public server and the liveness loop.
  - Nodes in tests start concurrently (errgroup).
  - Test: create topics and produce on a 3-node cluster, restart a node with no snapshot taken, and
    assert its partition dirs and data survive.
- **R2 (MAJOR 2)** Re-registration already applies fence semantics to partitions:
  `applyRegisterBroker` calls `fencePartitions`, and `TestReRegisterGivesUpLeadership` covers it.
  `UnfenceBroker` later re-elects with a new epoch.
- **R3 (MAJOR 3) Epochs on fence/unfence**: `FenceBrokerCommand` and `UnfenceBrokerCommand` gain
  `int64 broker_epoch = 2`. A mismatch with the current epoch, an already-fenced Fence, or an
  already-unfenced Unfence is a **no-op with no changes** (not an error). Table tests cover all
  three.
- **R4 (MAJOR 4) Leader-only writes and controller epochs**:
  - `metadata.Store` gains `ProposeAsLeader(ctx, cmd) error`. Raft: `raft.Apply` on this node, or
    `ErrNotController` if it is not leader; never forwarded. Local store: same as Propose.
  - `Snapshot` gains `ControllerEpoch uint64` (the Raft term the current leader won; 0 for the
    local store).
  - The controller's Register/Fence/Unfence and the coordinator's CommitOffsets use
    `ProposeAsLeader`.
  - The coordinator records the `ControllerEpoch` its groups belong to and clears all in-memory
    groups whenever it sees a different epoch or is not the controller. A regained leadership in a
    new term therefore starts empty.
  - Leadership fan-out: raftstore registers one `raft.Observer` for `LeaderObservation` and
    notifies any number of listeners (`OnLeadershipChange(fn) (cancel func())`); the controller uses
    it. hashicorp's single `LeaderCh` is not used.
  - Tests: a deposed controller's fence attempt is rejected; a coordinator that loses and regains
    leadership starts with no groups.
- **R5 (MAJOR 5) New controller catch-up**:
  - On gaining leadership the controller calls `Barrier()` (raftstore exposes it) and then
    activates.
  - Each tick takes the broker set from the current snapshot and starts a grace period for any
    broker not yet tracked.
  - A heartbeat from a fenced broker with no recorded `catchUpIndex` sets it to `CommitIndex()`
    at that moment.
  - The catch-up index of a registration is its `ApplyFuture.Index()`.
- **R6 (MAJOR 6) Restore resync**:
  - The `Restored` change carries the full `Snapshot` captured at that point under the FSM mutex
    (`Change.Snapshot *Snapshot`).
  - `broker.resync(snap)` is separate from the startup `applySnapshot`. It deletes local topics
    missing from the snapshot or with a different id (normal `deleteTopic` path), creates new ones,
    and applies leadership for every existing partition. It never runs the stray-dir pass.
  - `PartitionChanged` handling is monotonic: changes with a lower `leader_epoch` or
    `partition_epoch` than the partition's current one are ignored.
  - Test: InstallSnapshot to a lagging follower (low TrailingLogs, explicit `raft.Snapshot()`) after
    creating/deleting topics and moving leaders; its broker's partitions and leadership match the
    snapshot.
- **R7 (MAJOR 7) Forward semantics**:
  - A forward is retried automatically only when the entry was guaranteed not to be appended:
    `ErrNotController` returned before Apply, a dial/connect failure, or no leader known.
  - `ErrLeadershipLost` and RPC deadlines are returned as-is (unknown outcome).
  - `Propose` returns the Raft error from `ApplyFuture.Error()` and the FSM error from
    `Response()`.
  - The CreateTopic handler treats `ErrTopicExists` as success when the existing topic's id equals
    the proposed `topic_id`; DeleteTopic treats `ErrUnknownTopic` after a retry the same way.
- **R8 (MAJOR 8)** No split (see the top of this revision).
- **R9 (MAJOR 9) Injected listeners**:
  - raftstore takes a pre-bound `net.Listener` and uses a small `raft.StreamLayer` over it with
    `raft.NewNetworkTransport`.
  - `node.Start` accepts optional pre-bound listeners (client, internal, raft) via `node.Options`;
    production binds from config.
  - Tests bind `127.0.0.1:0` first and build the cluster config from the actual ports. A restart
    rebinds the same port with a bounded retry loop and fails clearly if it can't.
- **R10 (minor 10)** `applyCreate`: leader = first **unfenced** replica, ISR = replicas. If no
  replica is unfenced, the command fails with ErrInvalidReplicationFactor.
- **R11 (minor 11)** D36: RF must be ≤ the number of unfenced registered brokers (Kafka "usable
  brokers").
- **R12 (minor 12)**:
  - The FSM snapshot JSON is `{"version": 1, "state": {...}}`; Restore rejects unknown versions.
  - DECISIONS D37 records the `metadata.json`/snapshot broker fields (`internal_addr`, `fenced`,
    `epoch`) and the snapshot format as additive on-disk changes, and the direct
    `github.com/hashicorp/go-hclog` import. It is hashicorp/raft's logger interface, already in the
    module graph, needed for the slog adapter.
- **R13 (minor 13)** New `ERROR_CODE_STALE_BROKER_EPOCH = 22` (Kafka name). It is internal-API
  only and mapped only in `internal/server` (D13-style entry in D38).
- **R14 (minor 14)** Changes carry `Index uint64` (the Raft log index; a sequence number for the
  local store). The broker records the index of the last change it **finished processing**, and
  that is what the heartbeat reports as `applied_index` and what R1 waits on.
- **R15 (minor 15)** `ForwardMetadataResponse` gains `uint64 index = 4`. A forwarded `Propose`
  waits until the local FSM's applied index is ≥ that index (bounded by ctx) before returning, so
  the `Store.Propose` contract holds on followers.
- **R16 (minor 16)**:
  - `Close` order: `raft.Shutdown().Error()`, then `transport.Close()`, then the bolt stores, then
    the notifier.
  - `Apply` uses the ctx deadline (or 10 s) as its timeout.
- **R17 (minor 17) Timing**:
  - Snapshots are triggered explicitly in tests (`Snapshot()` method) with `TrailingLogs` low.
  - Integration config: `broker_session_timeout_ms` 2000, heartbeat 300, Raft
    heartbeat/election 300 ms.
  - Config validation requires `raft_election_timeout_ms >= raft_heartbeat_timeout_ms`.
  - The broker liveness loop and the controller take injected clocks.
- **R18 (minor 18)** `node.Start` fails fast if the data dir holds the other mode's metadata
  (`metadata.json` in cluster mode, or `raft/` in single-node mode).
- **R19 (minor 19)** Known M5 limitation, recorded in PROGRESS_LOG: with RF>1 there is no
  replication until M6. The HW only follows the LEO for ISR == {self} (D15), so on RF>1 partitions
  the HW stays at its checkpoint and acks=all appends wait for no one. M6 replaces this with the
  ISR-based HW and purgatory. RF>1 data-plane behaviour is not tested in M5.
- **R20 (minor 20)** `ForwardMetadata` accepts only CreateTopic and DeleteTopic. Anything else gets
  InvalidArgument.

### Decisions added (replacing §10's list where they overlap)
- D30 Single-node mode keeps the local JSON store and cluster mode uses raftstore. There is no
  migration, and mixing modes on one data dir fails fast (R18).
- D31 Broker-to-broker RPCs use a separate gRPC service on `internal_addr`.
- D32 Raft timing knobs are optional config keys, validated.
- D33 Server-side forwarding of CreateTopic/DeleteTopic from followers to the controller, retried
  only when the entry certainly was not appended. Controller and coordinator writes are
  leader-only.
- D34 Fencing keeps the last ISR member in the ISR. Offline partitions are re-elected when an ISR
  member is unfenced. Fence and unfence carry the broker epoch.
- D35 Registration fences (including partition effects). A broker is unfenced once it reports a
  processed metadata index ≥ the index of its registration entry, and it opens its partitions only
  after catching up (R1).
- D36 RF ≤ unfenced registered brokers.
- D37 On-disk additions (broker fields, versioned FSM snapshot) and the direct go-hclog import.
- D38 `STALE_BROKER_EPOCH` error code (internal API).

## Revision 2 (after plan-review round 2)

- **R21 (MAJOR 1) Defined processed index**:
  - `metadata.Snapshot` gains `Index uint64`: the index of the last entry applied into it,
    captured under the FSM mutex. Raftstore uses the Raft log index; the local store uses its
    change sequence number.
  - R1 step 5 waits on the raftstore FSM's `AppliedIndex() >= catch_up_index`, because the broker
    is not open yet.
  - `broker.Open` initialises its processed index from the Subscribe snapshot's `Index`. Every
    delivered change raises it to the change's `Index` after the handler finishes. The heartbeat
    reports that value.
  - Test: a fresh 3-node cluster with no topics has every broker unfenced (visible in `Metadata`
    brokers) within a bound; CreateTopic RF 3 then succeeds.
- **R22 (minor 2)** `applyCreate`: ISR = the **unfenced** replicas in replica order, and the leader
  is the first of them. If none are unfenced, the command fails with ErrInvalidReplicationFactor.
  Fenced replicas join the ISR later through replication (M6 expand).
- **R23 (minor 3) Term-bound leader commands**:
  - `MetadataCommand` gains `uint64 controller_epoch = 3`. The controller and coordinator set it to
    the term they acted in.
  - The raftstore FSM calls `State.ApplyInTerm(cmd, log.Term)`. A non-zero `controller_epoch` that
    differs from the entry's term is rejected deterministically with `ErrNotController`, leaving
    the state unchanged. `raft.Log.Term` is identical on every node.
  - `State.Apply(cmd)` (the local store) is `ApplyInTerm(cmd, 0)`; commands with epoch 0 are never
    term-checked.
  - The coordinator stamps commits with the epoch its groups belong to; the controller stamps
    Register/Fence/Unfence.
  - Test: a command stamped with an old term is rejected while the same command with the current
    term applies.
- **R24 (minor 4)** D33 notes that a client-level CreateTopic retry after an unknown outcome can
  report TOPIC_ALREADY_EXISTS for a create that succeeded (Kafka behaves the same). Admin already
  treats TOPIC_ALREADY_EXISTS after a transport-error attempt as success when the partition count
  matches (M3 R13). The server's same-`topic_id` check remains for its internal forward retries.
- **R25 (minor 5) ISR updates for a local leader**: `Partition.UpdateLeaderState(epoch, isr,
  partitionEpoch)`. On a `PartitionChanged` where the local broker stays leader at the same
  `leader_epoch` with a higher `partition_epoch`, the broker updates the ISR and re-runs
  `advanceHWLocked`. A higher `leader_epoch` goes through `BecomeLeader`/`BecomeFollower`, and
  lower epochs are ignored (R6). Broker test: a follower fenced → the leader's ISR shrinks → a
  min.insync check uses the new ISR.
