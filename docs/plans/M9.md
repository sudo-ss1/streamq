# M9 — Correctness & chaos (plan)

SPEC §9 M9: a Porcupine model for single-partition produce (acks=all) and fetch, plus chaos
scripts (kill -9 of random brokers, Toxiproxy partitions and latency, full-disk simulation).
✅ when `test/chaos/REPORT.md` documents the scenarios, the invariants checked and the results.
The failure-reviewer runs alongside the code-reviewer.

## 1. Linearizability model (`test/linearizability`, main session; it is the contract)

Package `linearizability`, with dependency `github.com/anishathalye/porcupine` (approved list).

**Operations on one partition**
- **Append(v)**: a single acks=all Produce attempt of one record with a unique value `v`.
  - OK result: the base offset `o`.
  - Definite failure: an error code that guarantees nothing was appended. These are
    `NOT_LEADER` or `FENCED_LEADER_EPOCH` *before* the append, which the broker rejects in
    `checkLeader`, and `NOT_ENOUGH_REPLICAS` before the append. Treated as no effect.
  - Unknown result: everything else (`REQUEST_TIMED_OUT`, `NOT_ENOUGH_REPLICAS` after the append,
    `NOT_LEADER` from a leader change while waiting, transport errors). The append may or may not
    have happened.
  - The client cannot tell the two `NOT_ENOUGH_REPLICAS` cases apart, nor the two `NOT_LEADER`
    cases, so every `NOT_LEADER` and `NOT_ENOUGH_REPLICAS` is classified as **unknown**. That is
    sound but weaker. The definite set is then `{UNKNOWN_TOPIC_OR_PARTITION, CORRUPT_MESSAGE,
    MESSAGE_TOO_LARGE}`.
- **Read()**: one Fetch of the whole partition from offset 0 up to the HW, via the broker the
  client believes is the leader, with `LeaderEpoch -1`. The result is the value sequence, or an
  error, which is treated as no effect.

**Model** (`porcupine.NondeterministicModel`)
- The state is the committed log (`[]string`).
- **Append OK(o)**: valid iff `len(state) == o`; the new state is `state + v`.
- **Append unknown**: two possible states, `{state, state + v}`.
- **Read(seq)**: valid iff `seq` is a **prefix** of `state`. It is a prefix, not equal, because
  Kafka consumer reads are not linearizable reads: a deposed leader, or a follower HW lagging
  within the leader's epoch, may serve a shorter committed prefix. Prefix still catches:
  - lost acknowledged appends: a later read would lack `v` while the model requires it;
  - reordering, and phantom or uncommitted data (values not in the state);
  - offsets that disagree with the log.
- **Durability:** a final quiescent Read from the settled leader (after the faults stop) must
  return the **full** state: every acked value plus some subset of the unknown ones. This runs as
  a separate check after the porcupine check passes, because porcupine's prefix rule alone allows
  a final short read.

**API (contract for package B)**
```go
type Recorder struct { /* mutex + []porcupine.Operation */ }
func NewRecorder() *Recorder
func (r *Recorder) Append(ctx context.Context, clientID int, c streamqv1.StreamQServiceClient, topic string, partition int32, value string) // records invoke/return
func (r *Recorder) Read(ctx context.Context, clientID int, c streamqv1.StreamQServiceClient, topic string, partition int32)
func (r *Recorder) History() []porcupine.Operation
func Check(ops []porcupine.Operation, timeout time.Duration) (porcupine.CheckResult, porcupine.LinearizationInfo)
func Model() porcupine.NondeterministicModel
func VerifyFinal(final []string, ops []porcupine.Operation) error // every acked value present, every value known, no duplicates
```
- Leader selection for clients is passed in (`LeaderFunc`), so the in-process test and the chaos
  runner share the code.
- Values are `"<client>-<n>"`.

**Tests**
- Model unit tests: hand-built histories:
  - accepted: sequential appends and reads; a concurrent read that sees or misses an in-flight
    append; an unknown append that later appears; one that never appears;
  - rejected: a lost ack (a later read lacks it), reordering, a phantom value, a wrong offset.
- **In-process linearizability test** (`lin_test.go`, build tag `integration`, run by
  `make test-int`, which gains `./test/linearizability/...`):
  - a 3-node cluster with RF 3 and min.insync 2; 4 concurrent clients on one partition for about
    20 s;
  - a fault loop with seeded randomness: graceful stop and restart of the current leader, then of
    a random follower; each restart waits for the ISR to recover;
  - porcupine check with a 60 s timeout, plus `VerifyFinal`;
  - on failure, write the porcupine visualization HTML to `t.TempDir()` and log its path;
  - expected op count ≥ 1000.

## 2. Chaos (`test/chaos`, implementer package B)

**Owned paths**
- `test/chaos/**`: the runner program at `test/chaos/cmd/chaos`, scenario code, and `REPORT.md`;
- `deploy/docker-compose.chaos.yml`: an override that puts broker3's data dir on a size-limited
  tmpfs, for full disk;
- Makefile `chaos` target: `go run ./test/chaos/cmd/chaos -compose deploy/docker-compose.yml
  -override deploy/docker-compose.chaos.yml -out test/chaos/results`.

**Depends on:** the §1 API (committed first), the compose stack (M8), the toxiproxy HTTP API, and
the docker CLI via `os/exec`.

**Runner**
- Brings the cluster up through compose and waits for `cluster status --strict`, using the
  streamqctl package logic via exec of the built binary.
- Creates topics, then runs each scenario for about 60–120 s while clients run:
  - the §1 recorder on a single-partition topic `lin` (RF 3, min.insync 2);
  - a throughput workload on topic `bulk`: an idempotent `pkg/client` producer with acks=all,
    keyed sequence values, 6 partitions.
- After the faults are healed and the cluster is healthy:
  - porcupine-check the `lin` history plus `VerifyFinal`;
  - for `bulk`: consume everything and check that every acked value is present exactly once
    (idempotence) and that per-key order holds.
- Writes per-scenario JSON results under `test/chaos/results/` (gitignored) and prints a summary.
- Every scenario resets the cluster (`down -v`, `up`) for independence.

**Scenarios**
1. `kill9-random`: every 10–20 s, `docker kill -s KILL` a random broker, then `docker start` it
   after 5–10 s. 4 rounds.
2. `kill9-controller`: kill -9 the current controller (from `cluster status`), 3 rounds.
3. `partition-leader`: isolate the `lin` partition leader by disabling both of its toxiproxy
   proxies (internal and Raft) for 15 s, then heal. Its client port stays reachable, so
   zombie-leader reads and appends are exercised. 3 rounds.
4. `latency`: add 200 ms ± 100 ms latency and 1% packet-ish slicing (`slicer`) toxics to all
   proxies for 60 s.
5. `full-disk`: broker3 runs on a 64 MiB tmpfs. Workloads continue until broker3's writes fail
   (ENOSPC). Expectations:
   - its partitions report errors, or the leadership moves after a restart;
   - no acked loss, and the other brokers keep serving;
   - after the space is freed (delete the topic `filler` or restart with a larger tmpfs), the
     cluster becomes healthy.

   The exact observed behaviour is documented, including whether the broker stays a failing
   leader (no log-dir failure handling exists; a known limitation, D56).

**Done criteria (B)**
- `make chaos` runs every scenario end to end and exits non-zero on any invariant violation.
- `go vet` and lint are clean (the runner builds under the default tags; it is not a test).
- `REPORT.md` contains, per scenario: the faults injected, the invariants checked, the op counts,
  the porcupine result, the acked/unknown/lost counts, the time to recover, and observations.
  Plus a summary table and the environment (CPU, RAM, Docker version).
- B reports any invariant violation to the main session as a FINDING with its reproduction and
  results file. B never fixes broker code.

## 3. Bug fixing (main session)
- Any violation found in §1 or §2 is fixed in the main session, with a regression test where
  feasible.
- Fixes to the M6 core (replication, HW, ISR, truncation) or the M7 sequence logic follow
  CLAUDE.md: main session only.
- The failure-reviewer reviews the fixes.

## 4. Decisions to add
- **D56:** the linearizability model: reads are prefix-checked (consumer reads are not
  linearizable in Kafka), plus a final-state durability check; NOT_LEADER and
  NOT_ENOUGH_REPLICAS are classified as unknown outcomes.
- **D57:** full-disk behaviour: no log-dir failure handling. A broker whose log fails returns
  errors for its partitions until it restarts; documented as a limitation.
- **D58:** porcupine is used with a 60 s check timeout, and a single partition keeps the checking
  tractable.

## Revision 1 (after plan-review round 1)

These rules supersede the text above where they conflict.

- **R1 (BLOCKER 1) Deterministic model, unknown appends open-ended.**
  - Unknown appends are recorded with `Return = math.MaxInt64`, because they may take effect
    after the client gives up.
  - The model is deterministic: an unknown append always applies `state + v`. "Never happened"
    is the same as linearizing it at the end of the history. `NondeterministicModel` is dropped.
- **R2 (MAJOR 2) A tractable check.**
  - (a) Before checking, drop every unknown append whose value appears in no successful read and
    not in the final log. This is sound: a value seen once must then be in the final log, or
    VerifyFinal fails.
  - (b) Clients back off 50–200 ms (jittered, seeded) after any error and skip attempts while no
    leader is known.
  - (c) A porcupine `Unknown` result (timeout) is a failure: "inconclusive", exit non-zero.
  - (d) Every run logs `Summary{Acked, DefiniteFail, Unknown, Pruned, Reads, FailedReads}`.
  - Recorded in D58.
- **R3 (MAJOR 3) Durability checks.** `VerifyFinal(final, ops)` requires:
  - `final[o] == v` for every acked `(v, o)`;
  - every successful read is a prefix of `final` (committed data is immutable);
  - every value in `final` was appended by some operation;
  - no value appears twice.

  The wording in §1 and D56 is corrected: reads check order and phantoms; durability comes from
  the offsets plus VerifyFinal.
- **R4 (MAJOR 4) Settling before the final read.**
  - After healing, a sentinel acks=all append is retried (bounded) until it is acked at offset `s`.
  - The final read is then retried until it includes offset `s`.
  - Only then does VerifyFinal run. `bulk` uses a sentinel per partition the same way.
- **R5 (MAJOR 5) Scenarios that cut traffic correctly.**
  - `partition-leader` becomes `inbound-isolation`, documented as an inbound-only cut. Its
    expected effects are ISR shrink and NOT_ENOUGH_REPLICAS, not zombie appends.
  - New scenario `pause-leader`: `docker pause` the `lin` leader for 12 s (more than the 9 s
    session timeout), then `docker unpause`. This is a GC-pause zombie.
  - A true symmetric partition needs NET_ADMIN and iptables. It is out of scope for M9 and listed
    as a REPORT limitation.
- **R6 (MAJOR 6) Full disk.**
  - The tmpfs override applies **only** to `full-disk`. No other scenario restarts a tmpfs broker.
  - The disk is filled with `docker exec broker3 dd`, writing a filler file inside the tmpfs.
  - Healing is an explicit disk replacement. Kill broker3, wait (via `cluster status`) until it is
    fenced and absent from every ISR, then start it empty.
  - The Raft state-loss caveat is in D57 and REPORT. Answer to the reviewer's question:
    disk-replacement healing is accepted (Kafka tie-breaker).
- **R7 (MAJOR 7) `bulk` invariants (consistent with D48):**
  - every acked value appears exactly once;
  - acked values of a key appear in sequence order;
  - a failed (not acked) value appears at most once, at any position, and is counted separately;
  - nothing appears that was never produced.
- **R8 (MINOR 8)** The contract commit makes both Makefile edits (`test-int` gains
  `./test/linearizability/...`, plus the `chaos` target) and adds `test/chaos/results/` to
  `.gitignore`. B owns only `test/chaos/**` and `deploy/docker-compose.chaos.yml`.
- **R9 (MINOR 9) Contract API.**
  - `type LeaderFunc func(ctx) (streamqv1.StreamQServiceClient, error)`; `Append` and `Read` take
    it.
  - Exported types: `Input{Kind, Value}` and `Output{Unknown, Offset, Values}`.
  - A single monotonic origin per Recorder.
  - `Summary` and `Recorder.Summary()`.
  - `Prune(ops, final)` implements R2a.
  - `WriteVisualization(path, info)`.
- **R10 (MINOR 10)** The state is immutable (an entry count plus an encoded string), so there is no
  aliasing. A unit test branches the same state twice.
- **R11 (MINOR 11) Classification table.**
  - Definite failures: `UNKNOWN_TOPIC_OR_PARTITION`, `CORRUPT_MESSAGE`, `MESSAGE_TOO_LARGE` and
    `INVALID_TIMESTAMP`.
  - Unknown: everything else, including `ERROR_CODE_UNKNOWN` and every gRPC error.
  - Each append is a non-idempotent batch with leader_epoch −1, `timeout_ms` below the RPC
    deadline, and exactly one attempt.
- **R12 (MINOR 12) In-process test.**
  - Faults are paced by completed operations: one fault every 150 ops, stopping at 1200 ops.
  - D56 states that crash coverage comes from the chaos runner, because in-process stops are
    graceful (D53).
  - `goleak.VerifyTestMain`. The model unit tests are untagged, so they run in `make test`.
- **R13 (MINOR 13)** D57 lists "broker crashes (SIGBUS on an mmapped index) or log marked failed"
  as acceptable full-disk outcomes. The invariants are: no acked loss, the other brokers keep
  serving, and after disk replacement broker3 catches up and rejoins the ISR.
- **R14 (MINOR 14) Runner practicality.**
  - Output goes through `fmt.Fprintf(os.Stdout, ...)`.
  - Scoped `nolint:gosec` on `exec.Command`.
  - Start only `toxiproxy broker1 broker2 broker3`, with project name `-p streamq-chaos`.
  - The `chaos` target depends on `build`.
  - Docker reachability is confirmed in the implementer's worktree as its first step; if
    unreachable, B reports it and the main session runs chaos itself.
- **R15 (MINOR 15)**
  - `slicer` is described as fragmentation plus delay.
  - REPORT separates availability (unavailability windows, recovery time) from safety.
  - Reads use `min_bytes=0` and `max_wait_ms=0`, loop on one broker up to the HW of the first
    response, and decode only up to that HW.

## Revision 2 (after plan-review round 2)

- **R16 (MAJOR 1) Unique sentinels.**
  - The `lin` clients are stopped and joined before settling.
  - Each sentinel attempt uses a fresh value `sentinel-<k>`, recorded through the Recorder.
  - `s` is the acked attempt's offset; the final read waits until `len(final) > s`.
  - `bulk` sentinels use the idempotent producer.
- **R17 (MAJOR 2) Read integrity anomalies.** `ReadAll` (now part of the contract) separates:
  - (a) transport errors and API ErrorCodes: no effect, counted in `FailedReads`;
  - (b) **integrity anomalies** below the HW: an offset gap, an offset going backwards, a CRC or
    decode failure, or no progress below the HW. These are returned as `*Anomaly{Broker, Offset,
    Err}` and recorded in `Summary.Anomalies`.

  Any anomaly fails the in-process test and makes `make chaos` exit non-zero. A unit test feeds a
  gapped fetch response from a fake server.
- **R18 (MAJOR 3) Current code in the REPORT.**
  - The runner runs `docker compose build` at start-up and records the image ID.
  - After merging B and after every §3 fix, the **main session** re-runs `make chaos` on merged
    main and writes the final REPORT.md: git SHA, image ID and results file names. Results from
    B's worktree count only as findings.
- **R19 (MINOR 4)** `docker-compose.chaos.yml` mounts a named volume at `/var/lib/streamq/raft`,
  nested inside the tmpfs. Only partition logs hit ENOSPC, healing is a true log-dir replacement,
  and the Raft caveat leaves D57.
- **R20 (MINOR 5)** The wait for "absent from every ISR" is bounded. On timeout the scenario
  records "partition offline (availability)" with the list and skips the empty restart.
- **R21 (MINOR 6)** UNKNOWN_TOPIC_OR_PARTITION becomes **unknown** (`storage.ErrClosed` can follow
  a partial write). Definite failures: CORRUPT_MESSAGE, MESSAGE_TOO_LARGE and INVALID_TIMESTAMP,
  all validation errors before any write. D56 notes that a misclassified definite failure would
  surface as a phantom in VerifyFinal.
- **R22 (MINOR 7)** Before checking, every unknown append's Return is set to (max finite
  timestamp + 1). The semantics are unchanged and the visualization stays readable.
- **R23 (MINOR 8)** VerifyFinal runs **before** the porcupine check. Each unknown append whose
  value is in `final` is pinned to an expected offset (its index in `final`); unknown appends that
  are neither read nor in `final` are pruned. Helper: `Prepare(ops, final) []porcupine.Operation`.
- **R24 (MINOR 9)** The visualization goes to `$STREAMQ_LIN_OUT` (default `os.TempDir()`) and the
  path is logged.
- **R25 (MINOR 10)**
  - The contract includes `ReadAll` and `Anomaly`. goleak's `TestMain` lives in an untagged
    `main_test.go`.
  - The `bulk` producer is flushed and closed before the final consume; unsent values count as
    failed.
  - The runner fails fast if the host ports 9092/9192/9292/8474 are already bound.
  - REPORT states that `docker kill -9` keeps the host page cache, so fsync and power-loss
    durability are not exercised.

## Revision 3 (MINORs adopted from plan-review round 3)

- **R26. Full-disk mechanics** (all within B's paths):
  - `deploy/docker-compose.chaos.yml` overrides broker3's `/var/lib/streamq` volume entry with a
    named volume `broker3-logs` using the local driver,
    `driver_opts: {type: tmpfs, device: tmpfs, o: "size=64m,uid=65532,gid=65532"}`.
  - Separately, `broker3-raft` is mounted at `/var/lib/streamq/raft`. A one-shot busybox service
    chowns it to 65532:65532, and broker3 depends on it with
    `condition: service_completed_successfully`.
  - The disk is filled through a helper container:
    `docker run --rm -v <project>_broker3-logs:/d busybox dd ...` (the distroless image has no
    shell).
  - Healing:
    1. kill broker3;
    2. the bounded R20 wait;
    3. `docker volume rm` and recreate `broker3-logs`;
    4. start broker3.
- **R27. Read anomalies without false positives.**
  - "No progress" counts as an anomaly only when **that response's own** HW is above the requested
    offset. Otherwise the read ends as a no-effect failed read (the HW of a re-elected leader can
    lag).
  - Records below the requested offset are skipped before the gap check.
  - Done in the contract code.
- **R28. pause-leader.** The pause is ≥ 20 s. Each round records whether the `lin` leader epoch
  changed; a round without a change is reported as "fault not exercised", not as a pass.
- **R29. Container targeting.**
  - Every container action goes through `docker compose -p streamq-chaos -f ... kill|pause|`
    `unpause|start <service>`, or uses IDs from `docker compose ps -q`.
  - The override sets an image tag `streamq:chaos`, so the dev cluster's `streamq:dev` is never
    re-tagged.
- **R30. Seeds.** The in-process test logs its seed, and `STREAMQ_LIN_SEED` overrides it. The
  runner writes its seed into every results JSON and into REPORT.
