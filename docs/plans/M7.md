# M7 — Idempotent producer (plan)

SPEC §6 and §9 M7. Acceptance criteria:
- A producer with injected network failures and retries produces no duplicates and no reordering.
- Producer state survives leader failover and broker restart.

All work runs in the main session. The sequence logic (`internal/producerstate`, the partition
append path and the client sequence assignment) is correctness-critical and must not be
parallelized (CLAUDE.md). The remaining pieces (proto, ID allocation) are small and coupled to the
same contract, so they are not worth splitting. There are no implementer packages.

## 1. Protocol (additive, non-breaking)

**`api/v1/streamq.proto`**
- `rpc InitProducer(InitProducerRequest) returns (InitProducerResponse)`.
- `InitProducerRequest {}`.
- `InitProducerResponse { ErrorCode error_code = 1; string error_message = 2; int64 producer_id = 3;
  int32 producer_epoch = 4; }`.

**`api/v1/internal.proto`**
- `rpc AllocateProducerIDs(AllocateProducerIDsRequest) returns (AllocateProducerIDsResponse)`, served
  by the controller.
- `AllocateProducerIDsRequest { int32 broker_id = 1; int64 broker_epoch = 2; }`.
- `AllocateProducerIDsResponse { ErrorCode error_code = 1; string error_message = 2;
  int64 first_id = 3; int32 count = 4; int32 controller_id = 5; }`.
- `MetadataCommand` oneof gains `AllocateProducerIDsCommand allocate_producer_ids = 17`, with
  fields `{ int32 broker_id = 1; }`.

Batches already carry `producerID`, `producerEpoch` and `baseSequence` (§3.5), so
`ProduceRequest` is unchanged.

## 2. Producer-ID blocks (`internal/metadata`, `internal/controller`, `internal/server`, `internal/node`)

**FSM state**
- `NextProducerID int64`, starting at 0.
- `ProducerIDBlocks map[int32]int64`: the last block start handed to each broker.
- Both are persisted in snapshots (additive JSON keys) and covered by `TestPersistedJSONKeys`.

**`applyAllocateProducerIDs`**
- The broker must be registered.
- Sets `ProducerIDBlocks[b] = NextProducerID` and `NextProducerID += ProducerIDBlockSize` (1000).
- Emits `Applied` only.
- Deterministic, and term-bound like the other controller commands.

**`controller.AllocateProducerIDs(ctx, brokerID, brokerEpoch) (first int64, err)`**
- Checks the active term.
- Checks that the broker epoch matches (`ErrStaleBrokerEpoch` otherwise).
- Applies the command through `ApplyForwarded`, then reads `ProducerIDBlocks[brokerID]` from the
  leader's own snapshot. `ApplyForwarded` returns after the local FSM apply, and the broker
  serializes its own requests, so the value read is this request's block.

**Broker-side allocator (`internal/broker/producerids.go`)**
```go
type IDBlockSource func(ctx context.Context) (first int64, err error)
type ProducerIDs struct { mu sync.Mutex; next, end int64; src IDBlockSource }
func (a *ProducerIDs) Next(ctx context.Context) (int64, error)
```
- Under `mu`, a new block is requested when the current one is exhausted.
- An error from the source is returned to the caller. Nothing is cached, so the next call retries.
- A lost response (unknown outcome) only wastes IDs; it never duplicates them.

**Sources**
- Cluster mode: `server.ReplicaClient.AllocateProducerIDs`, an internal RPC to the controller.
  - It resolves the controller address from metadata.
  - `NOT_CONTROLLER` and transport errors are retriable for the client and map to
    `NOT_CONTROLLER` / `REQUEST_TIMED_OUT`.
- Single-node mode: `local.Store.Propose(AllocateProducerIDs{self})`, then read
  `ProducerIDBlocks[self]`. The local store applies commands synchronously, so the read is exact.

**`Server.InitProducer`** calls `ProducerIDs.Next` and returns `{producer_id, producer_epoch: 0}`.
Errors map in `server.errorCode`.

## 3. Producer state (`internal/producerstate`)

```go
const MaxBatchesPerProducer = 5

type BatchMeta struct { FirstSeq, LastSeq int32; FirstOffset, LastOffset, MaxTimestamp int64 }

type entry struct { Epoch int16; Batches []BatchMeta /* oldest first, <= 5 */; LastTimestamp int64 }

// State is one partition's producer state; it is not safe for concurrent use (the partition
// serializes access).
type State struct { producers map[int64]*entry; dir string; expiration time.Duration }

func New(dir string, expiration time.Duration) *State

// Check validates an idempotent batch on the leader.
// Returns (dup, true, nil) for a duplicate, (_, false, nil) when the batch may be appended,
// ErrOutOfOrderSequence or ErrUnknownProducerID otherwise.
func (s *State) Check(pid int64, epoch int16, firstSeq, lastSeq int32) (BatchMeta, bool, error)

// Update records an appended batch (leader and follower, and replay); non-idempotent batches
// (pid == record.NoProducerID) are ignored.
func (s *State) Update(pid int64, epoch int16, m BatchMeta)
```

**Check rules (Kafka)**
- Unknown pid:
  - `firstSeq == 0` → accept;
  - otherwise → `ErrUnknownProducerID`.
- Known pid:
  - **Duplicate:** an exact `(FirstSeq, LastSeq)` match among the last 5 batches. Return it.
  - **In sequence:** `firstSeq == nextSeq(last.LastSeq)`, where `nextSeq` wraps `MaxInt32 → 0`.
    Accept.
  - Anything else (a gap, a partial overlap, or a duplicate older than the last 5) →
    `ErrOutOfOrderSequence`.
- `lastSeq` is `firstSeq + records - 1`, with wraparound (Kafka).
- A batch with a sequence but `pid < 0`, or `pid >= 0` with `baseSequence < 0`, gets
  `ErrInvalidProducerBatch`. It maps to `CORRUPT_MESSAGE`; this is a validation-only addition.
- The epoch is stored but not checked: §3.5 says "0 for now".

**Snapshots** (SPEC §3.1, §6)
- `WriteSnapshot(ctx, offset)` writes `<20-digit offset>.snapshot`. It holds the state of all
  batches with `LastOffset < offset`.
- File format: a 4-byte big-endian CRC32C, then a JSON body
  `{"version":0,"offset":N,"producers":[{"id","epoch","last_timestamp","batches":[...]}]}`.
- Written via tmp + fsync + rename + dir fsync.
- `LoadLatest(ctx, maxOffset)`:
  - deletes snapshots with offset > `maxOffset`;
  - loads the newest valid one ≤ `maxOffset`;
  - deletes corrupt or unparsable ones (logged) and falls back to older snapshots or to empty
    state;
  - returns the snapshot offset, or `logStart` when there is none.
- `TruncateSnapshots(offset)` deletes snapshots with offset > `offset`.
- `DeleteSnapshotsBelow(logStart)` deletes snapshots with offset < `logStart`.
- `Clear()` empties the state and deletes all snapshots (full truncation).

**Rebuild**
```go
func (s *State) Rebuild(ctx context.Context, src BatchReader, logStart, leo int64) error
```
- Calls `LoadLatest(leo)`, then replays batch headers from `max(snapOffset, logStart)` up to `leo`.
- `BatchReader` is the consumed interface `Read(ctx, start int64, maxBytes int, maxOffset int64)
  (storage.ReadResult, error)`. It reads in 1 MiB chunks with `record.SplitBatches`.

**Expiration**
- `ExpireBefore(nowMs)` drops producers with `LastTimestamp < nowMs - expiration`.
- `LastTimestamp` is the batch max timestamp (Kafka's `lastTimestamp`), so it is deterministic on
  replay.
- Producers are not evicted when retention moves the log start, only by expiration. This differs
  from Kafka's log-start eviction; see D49.

## 4. Partition integration (`internal/partition`)

**Lock order:** `Partition.mu → Partition.prodMu → (storage) → Partition.hwMu`. `prodMu` serializes
check → append → update, plus snapshot writes and rebuilds.

**`New`** takes the producer `State`. `broker.openPartition` builds it and calls
`Rebuild(log, logStart, LEO)` before the first transition.

**`Append`** (leader)
- Non-idempotent batches: unchanged, apart from taking `prodMu` around the append so that a roll
  snapshot is consistent.
- Idempotent batches (`pid >= 0`):
  - Under `prodMu`, call `Check`.
  - A duplicate returns `AppendInfo{FirstOffset: dup.FirstOffset, LastOffset: dup.LastOffset}`
    with no append. The current epoch is returned, so acks=all waits for `HW > dup.LastOffset`.
  - Otherwise append, and if the log rolled, write the snapshot at the new base. That base equals
    this batch's base offset, so the snapshot excludes the batch. Then `Update`.

**`storage.AppendInfo`** gains `RolledAt int64`: the new segment's base if this append rolled,
else -1. `storage.Log.Append` and `AppendAsFollower` set it.

**`AppendAsFollower`** does the same under `prodMu`, with no check: snapshot-on-roll, then `Update`.

**Truncation**
- `TruncateTo` (follower):
  - after the log and epoch truncation, `state.TruncateSnapshots(newLEO)`;
  - then `Rebuild(log, logStart, newLEO)`, under `prodMu`;
  - a rebuild error fails the truncation and the fetcher retries.
- `TruncateFullyAndStartAt` calls `state.Clear()`.

**Maintenance:** `Partition.ExpireProducers(now)` and `Partition.SyncLogStart` (which also calls
`DeleteSnapshotsBelow(logStart)` when the log start changed) run from the broker's ISR loop tick
(under `applyMu`, as in M6).

A snapshot write failure on roll is logged and does not fail the append. Recovery just replays
more. This matches Kafka, where snapshots are an optimization.

## 5. Server and broker
- `errorCode`:
  - `producerstate.ErrOutOfOrderSequence` → `OUT_OF_ORDER_SEQUENCE`;
  - `ErrUnknownProducerID` → `UNKNOWN_PRODUCER_ID`;
  - `ErrInvalidProducerBatch` → `CORRUPT_MESSAGE`.
- `Broker.Produce` is unchanged; the partition does the work. A duplicate's result reports the
  original base offset.
- `node` wires `ProducerIDs` with the cluster or single-node source and passes it to `server.New`.

## 6. Client (`pkg/client`)

**Config**
- `ProducerConfig.Idempotent`: idempotence is enabled when `Acks == AcksAll` unless
  `DisableIdempotence` is set (Kafka ≥ 3.0 default, D48).
- With `Acks != AcksAll`, idempotence is off. Setting `Idempotent` explicitly with acks ≠ all is a
  config error.

**Producer ID**
- `producerID` is initialized lazily on the first send, via `callAny(InitProducer)`, under a
  producer-level mutex, and retried with backoff while within the delivery timeout.
- The `(pid, epoch)` is cached.

**Sequences**
- Per partition: `seqPID int64` and `nextSeq int32`.
- The sequence is assigned on a batch's first send attempt and stays fixed for retries:
  - `b.pid, b.seq = pid, nextSeq`;
  - `nextSeq += len(recs)`, with wraparound;
  - if `seqPID != pid`, first `nextSeq = 0` and `seqPID = pid`.
- One batch is in flight per partition (existing D21). This satisfies "≤ 5 in flight", and
  ordering follows directly.

**Retries**
- Every attempt re-encodes with the same `(pid, epoch, seq)`, so the leader dedups after a lost
  response.

**Failure handling**
- MESSAGE_TOO_LARGE split: nothing was appended and nothing later was sent, so roll back
  `nextSeq = b.seq` and let the halves take fresh sequences.
- Any other final failure of a batch that had a sequence (delivery timeout, non-retriable error,
  OUT_OF_ORDER_SEQUENCE, UNKNOWN_PRODUCER_ID) marks the producer for re-initialization. The next
  sequence assignment first obtains a new pid, so later batches never sit behind a sequence gap.
  The failed batch itself was reported to the application, so nothing is silently retried under a
  new identity (Kafka's epoch bump, D48).
- `OUT_OF_ORDER_SEQUENCE` and `UNKNOWN_PRODUCER_ID` are non-retriable for the batch.

**Fake server:** the existing fake in `pkg/client/fake_test.go` gains `InitProducer` and a
sequence-dedup option for unit tests.

## 7. Tests

**`producerstate`**
- `Check` table:
  - new pid with seq 0 / seq 5;
  - in-sequence;
  - a duplicate of each of the last 5;
  - a duplicate older than 5 → OOO;
  - gap;
  - partial overlap;
  - wraparound at `MaxInt32`.
- `Update` keeps 5.
- Snapshot round trip.
- A corrupt CRC is skipped and an older snapshot is used.
- `LoadLatest` deletes snapshots above `maxOffset`.
- `Rebuild` from a snapshot plus replay equals the live state.
- Expiration.
- goleak.

**`partition`**
- A duplicate returns the original offsets with no append.
- OOO and unknown-pid errors append nothing.
- A roll writes a snapshot that excludes the rolling batch.
- After a reopen, a duplicate is still detected (snapshot + replay).
- Follower `AppendAsFollower` updates state, so a promoted follower detects a duplicate.
- `TruncateTo` rebuilds: a batch truncated away is no longer a duplicate, and its retry is
  appended.
- `TruncateFullyAndStartAt` clears state.

**`storage`**: `RolledAt` is set on roll, for both append paths.

**`metadata`**
- The `AllocateProducerIDs` FSM table: unregistered broker, monotonic blocks, per-broker record.
- Snapshot round trip includes the new fields.

**`controller`/`server`**
- `AllocateProducerIDs` returns distinct blocks.
- `ProducerIDs` allocator: rolls to a new block after 1000, retries after a source error, and is
  safe under concurrent `Next` with `-race`.

**`client`**
- A fake drops the response after appending once (lost ack). The retry gets the dup result, and
  the callbacks see each record exactly once at its original offset.
- After a delivery-timeout failure, the next batch uses a new pid with seq 0.
- A split rolls back the sequence.
- `DisableIdempotence` sends `pid -1`.

**Integration (`test/integration/idempotent_test.go`, 3-node cluster, RF 3, min.insync 2)**
1. **Lost responses.** A client `DialOptions` unary interceptor fails a share of Produce calls
   *after* the server responded (returns `codes.Unavailable`, dropping the response) and some
   *before* sending.
   - Produce 3000 sequence-numbered values across 3 partitions (by key).
   - Consume everything: every acknowledged value appears exactly once, and per-key order is
     preserved.
   - With a seeded RNG, at least one injected lost-after-append must have happened (asserted
     through an interceptor counter).
2. **Leader failover.** Continuous idempotent production with injected lost responses. Stop the
   partition leader mid-stream, keep producing until ≥ 100 acks after the new leader appears,
   then check no duplicates and no reordering. Duplicates must be detected by the new leader,
   which has replicated producer state.
3. **Broker restart.** Produce, restart every broker one at a time (rolling, waiting for a full
   ISR between restarts), then resend with the same pid and an old sequence through a raw
   `Produce` using a hand-built batch → a duplicate result with the original offset, and the
   partition LEO unchanged. `segment_bytes` is small so rolls write snapshots, which exercises
   snapshot + replay.

## 8. Decisions (to add)
- **D48** Client idempotence:
  - on by default with acks=all;
  - the sequence is assigned on first send;
  - one batch in flight per partition;
  - after an unknown-outcome failure, re-initialize the pid instead of an epoch bump. The producer
    epoch stays 0.
- **D49** Producer-state eviction is only by `producer_id_expiration_ms`, measured on the batch
  max timestamp. There is no log-start eviction. An unknown pid with seq ≠ 0 →
  UNKNOWN_PRODUCER_ID, which is non-retriable; the client re-inits.
- **D50** Producer snapshots:
  - written synchronously on roll, as a CRC32C + JSON file;
  - a failure to write one is not fatal;
  - recovery uses the newest valid snapshot ≤ LEO and replays the rest;
  - snapshots below the log start are deleted.
- **D51** Producer IDs:
  - blocks of 1000, one per broker per request, recorded in FSM state as
    `ProducerIDBlocks[broker]`;
  - single-node mode uses the local store;
  - IDs wasted on lost responses are acceptable.

## Revision 1 (after plan-review round 1)

These rules supersede the text above where they conflict.

- **R1 (MAJOR 1) Atomic rebuild and invalid state.**
  - `Rebuild` builds into a fresh map, replays into it, and swaps it in only on success.
  - On any failure the partition marks producer state **invalid**: `prodValid = false`, under
    `prodMu`.
  - While invalid:
    - an idempotent `Append` returns `ErrNotLeader` (retriable; the client refreshes and retries),
      and nothing is appended;
    - `BecomeLeader`, every later `TruncateTo` (even a no-op) and the ISR-loop tick retry the
      rebuild.
  - Non-idempotent appends are unaffected.
  - Test: inject a `BatchReader` error into the rebuild in `TruncateTo`, promote the replica, and
    resend the truncated batch. It gets `NOT_LEADER` and no duplicate result. After the reader
    recovers, the next tick or `BecomeLeader` rebuilds, and the resend is appended as new.
- **R2 (MAJOR 2) Stale snapshots below the log start.**
  - `TruncateFullyAndStartAt` deletes all snapshots and fsyncs the dir **before** the log
    truncation, the same order as the epoch cache.
  - `Rebuild(ctx, src, logStart, leo)` first deletes snapshots with offset < `logStart` or
    > `leo`, ignores them for loading, then loads the newest valid one in `[logStart, leo]`.
  - With no snapshot it starts empty and replays from `logStart`.
  - Test: a stale snapshot below the log start is ignored and deleted.
- **R3 (MAJOR 3) Validate before Check.**
  - `storage.Log` exposes `ValidateForAppend(b []byte) (record.Batch, error)`, which covers
    length, CRC, canonical form, `max.message.bytes` and the timestamp checks currently inside
    `Append`.
  - It also exposes `AppendValidated(ctx, batch, leaderEpoch)`, which skips revalidation.
    `Append` becomes `ValidateForAppend` + `AppendValidated`.
  - `Partition.Append` validates first, then applies the producer-field consistency check
    (`ErrInvalidProducerBatch`), then `Check`, then `AppendValidated`.
  - Tests: a batch shorter than 61 bytes, and a bad-CRC batch whose (pid, seq) matches a stored
    batch, both get `CORRUPT_MESSAGE` with no panic.
  - `AppendAsFollower` already validates inside storage. The partition reads producer fields only
    after storage accepted the batch.
- **R4 (MAJOR 4) FSM field propagation tests.**
  - `Clone()` and `Snapshot()` copy `NextProducerID` and `ProducerIDBlocks`.
  - Tests:
    - local store: allocate, `CreateTopic`, allocate → distinct blocks; reopen `metadata.json` →
      the counter persisted;
    - raftstore FSM `Apply`: allocate, unrelated command, allocate → distinct blocks;
    - FSM snapshot/restore round trip includes the fields;
    - the existing deep-copy test covers the map.
- **R5 (MAJOR 5) Deterministic failover dedup.**
  - Integration test 2 first sends a hand-built idempotent batch (pid from `InitProducer`, seq 0)
    with acks=all through a raw `Produce`, and records its base offset.
  - It waits for the full ISR, stops the leader, waits for the new leader, resends the identical
    bytes, and asserts the original base offset with the new leader's LEO unchanged.
  - The randomized lost-response stream still runs.
  - The test asserts the injected-loss counter > 0 over the whole run, not specifically during
    failover.
- **R6 (MINOR 6) Allocation result.**
  - `controller.AllocateProducerIDs` holds a controller `allocMu` across the apply and the read of
    `ProducerIDBlocks[b]`.
  - Every allocation goes through the active controller's term-stamped commands; an older term's
    commands are rejected by the FSM. So no other allocation for `b` can be applied between the
    two steps.
  - The single-node allocator applies and reads under its own mutex.
  - This avoids widening the Store interface to return FSM responses. Override recorded here; the
    uniqueness argument does not depend on broker-side serialization.
- **R7 (MINOR 7) Ctx and locks.**
  - Every file-touching producerstate method takes `ctx` first: `WriteSnapshot`, `Rebuild`,
    `TruncateSnapshots`, `DeleteSnapshotsBelow`, `Clear`.
  - `LoadLatest` is internal to `Rebuild`, which receives `logStart`.
  - `SyncLogStart`, `ExpireProducers`, the snapshot write and `Rebuild` all run under `prodMu`.
- **R8 (MINOR 8)** `Rebuild` deletes `*.snapshot.tmp` leftovers. Tested.
- **R9 (MINOR 9) No needless rebuilds.**
  - `TruncateTo` rebuilds only when the LEO changed or the state is invalid.
  - On a clean `Close`, the broker writes a snapshot at the LEO for each partition (Kafka), so a
    clean restart replays nothing.
  - Pre-M7 data dirs replay once, on first open.
- **R10 (MINOR 10)** Integration test 3 resends the exact bytes of one of the pid's last 5 batches
  and asserts that `.snapshot` files exist before the restarts.
- **R11 (MINOR 11)** D51 records that `metadata.json` and the Raft snapshot gain
  `next_producer_id` and `producer_id_blocks`, and that older files load as 0 and empty.
- **R12 (MINOR 12) Client pid locking.**
  - A dedicated `pidMu` (a leaf) guards `(pid, epoch, pidGen, needReinit)`. It is held across the
    InitProducer RPC and never taken under `Producer.mu` or `partitionState.mu`.
  - Each batch records the `pidGen` it was sequenced under. Only a final failure under the
    current `pidGen` sets `needReinit`.
  - D48 notes two points:
    - Without epoch fencing, a timed-out batch still being processed on the server may land after
      later batches. This is acceptable: the application was told it failed.
    - One batch in flight per partition limits throughput; M10 will measure it.

## Revision 2 (MINORs adopted from plan-review round 2)

- **R13 (R6 corrected).** `controller.AllocateProducerIDs` holds `allocMu` across apply and read. After
  reading `ProducerIDBlocks[b]`, it requires `store.Term() == term` and `activeTerm() == term`;
  otherwise it returns `ErrNotController` (retriable; a block is wasted).
  - Correct argument: any entry from a later term T' > T that this node applied has already
    raised its Raft term past T. So when the term is still T, the value read is from this node's
    own apply, and no other term-T controller exists.
  - The controller.go lock header gains: `allocMu → store calls; never taken under mu`.
- **R14.** The deterministic failover probe (R5) uses a dedicated topic that the random stream does
  not write to, so "LEO unchanged" is exact.
- **R15.** Raw-Produce test helpers stamp batches with `time.Now()`. A producerstate unit test
  documents "expired pid + seq 0 → accepted as new".
- **R16.** On `Broker.Close`, the LEO snapshot is written for each partition after
  `BeginShutdown` (appends blocked by `Remove`), `stopAllFetchers` and `group.Wait()`, after
  flushing that partition's log, and before `mgr.Close`. Integration test 3 makes one restart a
  SIGKILL, using the `kill_test.go` broker-process harness, so recovery replays from a roll
  snapshot.
- **R17.** A rebuild failure in `BecomeLeader` or `openPartition` only sets `prodValid=false` and
  logs. The transition or open succeeds, and the ISR-loop tick retries.
- **R18.** The client has only `DisableIdempotence bool`. Idempotence is enabled iff
  `Acks == AcksAll && !DisableIdempotence`; there is no error case. Existing producer unit tests
  keep their assertions, and the fake gains `InitProducer`. Any test edit beyond the fake is
  listed in the code review and logged in DECISIONS (D48).
- **R19.** D49 records the known state-loss cases: full truncation on a follower that is later
  promoted, and a missing roll snapshot at the log start after retention. Affected producers get
  UNKNOWN_PRODUCER_ID and re-init (Kafka-like).
- **R20.** `Rebuild` retries once with the log's current start when replay hits
  `storage.ErrOffsetOutOfRange` (retention raced it). It needs the log start, so `BatchReader`
  gains `LogStartOffset() int64`. Unit-tested.
