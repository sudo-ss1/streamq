# M3 — Client library (plan)

SPEC refs: §7.4 (partitioning: murmur2 for keys, sticky for unkeyed), §8 FR3 (per-key order), FR12
(metadata cache + refresh on NOT_LEADER/FENCED_LEADER_EPOCH, retries with exponential backoff and
jitter, batching via `linger.ms`/`batch.size`, `Close` flushes), §9 M3. Acceptance (§9): examples run
end-to-end; tests for retry on injected errors and for `Close` flushing.

Out of scope: consumer groups / `GroupConsumer` (M4), idempotence / `InitProducer` / multiple
in-flight batches per partition (M7), multi-broker failover behaviour beyond what metadata refresh
gives (exercised in M6), metrics (M8).

No new dependencies.

### 1.1 Client core (main session, written and tested before the split)
```go
type Config struct {
    Bootstrap      []string        // "host:port", at least one
    RequestTimeout time.Duration   // per RPC, default 30s
    MetadataMaxAge time.Duration   // periodic refresh age, default 5m (refresh is lazy, on use)
    RetryBackoff   time.Duration   // base, default 100ms
    RetryBackoffMax time.Duration  // cap, default 1s
    DialOptions    []grpc.DialOption // appended (tests inject bufconn dialers)
    Logger         *slog.Logger    // default discard
}
func New(cfg Config) (*Client, error)        // validates; no I/O (lazy connect, gRPC NewClient)
func (c *Client) Close() error               // closes all connections
// internal, used by Producer/Consumer/Admin:
func (c *Client) anyBroker(ctx) (streamqv1.StreamQServiceClient, error)    // bootstrap or known broker
func (c *Client) leaderFor(ctx, tp) (streamqv1.StreamQServiceClient, partitionInfo, error)
func (c *Client) refreshMetadata(ctx, topics []string) error  // single-flight per call set
func (c *Client) invalidate(topic string)                      // on NOT_LEADER/FENCED/UNKNOWN
func (c *Client) partitions(ctx, topic) (int32, error)          // count, from cache (refresh if missing)
```
Metadata cache: `topics map[string]topicInfo{partitions []partitionInfo{leader, epoch}}`,
`brokers map[int32]string`. A refresh asks one broker (bootstrap addresses in order, then known
brokers) for `Metadata(topics)`; on transport error it tries the next. Connections are cached per
address (`grpc.NewClient`, insecure, 64 MiB call limits — D19). Concurrency: `Client.mu`
(RWMutex) guards cache + conn map; refresh does its RPC outside the lock and installs results
under it; concurrent refreshes of the same topic coalesce via a `singleflight`-style map of
in-flight calls (hand-rolled; `golang.org/x/sync/singleflight` is part of the approved
`golang.org/x/sync` module).

Errors (`errors.go`): `ServerError{Code streamqv1.ErrorCode; Message string}` with
`Is(target)` matching exported sentinels (`ErrNotLeader`, `ErrFencedLeaderEpoch`,
`ErrUnknownTopicOrPartition`, `ErrTopicAlreadyExists`, `ErrMessageTooLarge`, `ErrCorruptMessage`,
`ErrNotEnoughReplicas`, `ErrRequestTimedOut`, `ErrOffsetOutOfRange`, `ErrInvalidReplicationFactor`,
`ErrInvalidConfig`, `ErrInvalidTopic`, `ErrInvalidTimestamp`, … one per code).
`IsRetriable(err)`: NOT_LEADER, FENCED_LEADER_EPOCH, UNKNOWN_TOPIC_OR_PARTITION (metadata may be
stale), NOT_ENOUGH_REPLICAS, REQUEST_TIMED_OUT, and gRPC `Unavailable`/`DeadlineExceeded`/
`ResourceExhausted`/`Aborted` transport errors; everything else is fatal for that batch.
`needsMetadataRefresh(err)`: NOT_LEADER, FENCED_LEADER_EPOCH, UNKNOWN_TOPIC_OR_PARTITION,
transport errors.

Backoff (`backoff.go`): attempt n → `rand[0, min(max, base·2^n)]` ("full jitter"); the rand
source is injectable (`func() float64`) so tests are deterministic.

## 2. Producer (`producer.go`, `accumulator.go`)

```go
type Acks int  // AcksNone, AcksLeader, AcksAll (default AcksAll)
type ProducerConfig struct {
    Acks Acks; Linger time.Duration /* default 5ms */; BatchSize int /* bytes, default 16 KiB */
    BufferMemory int /* bytes buffered before Produce blocks, default 32 MiB */
    DeliveryTimeout time.Duration /* default 2m: first append → final failure */
    Partitioner Partitioner /* default: murmur2 for keyed, sticky for unkeyed */
    Now func() time.Time /* default time.Now */
}
type Partitioner interface { Partition(topic string, key []byte, numPartitions int32) int32;
    OnNewBatch(topic string, prevPartition int32, numPartitions int32) }   // sticky hook
func NewProducer(c *Client, cfg ProducerConfig) (*Producer, error)
func (p *Producer) Produce(ctx, rec Record, cb func(RecordMetadata, error)) error
    // async; error only if closed / ctx done while blocked on BufferMemory / invalid record.
    // cb runs on the partition's sender goroutine, in record order per partition.
func (p *Producer) ProduceSync(ctx, rec Record) (RecordMetadata, error)
func (p *Producer) Flush(ctx) error   // seal open batches, wait until every buffered record completed
func (p *Producer) Close(ctx) error   // stop accepting, Flush, stop senders; idempotent
```
Design:
- **Accumulator**: per partition an open `record.Builder` + callbacks. Records append to the open
  batch; when its encoded size would exceed `BatchSize` (or `MaxMessageBytes` guard of 1 MiB) it is
  sealed. The first record of an open batch arms a linger timer (`time.AfterFunc`, stopped on seal)
  that seals it after `Linger`. Sealed batches go on the partition's queue.
- **Ordering (FR3)**: one sender goroutine per partition sends its queue strictly in order with **at
  most one batch in flight** (retries included), so retries can never reorder records of a key.
  (M7 raises this to 5 with idempotent sequence numbers.)
- **Sticky partitioner** (§7.4): unkeyed records go to `sticky[topic]`; when that partition's open
  batch is sealed, `OnNewBatch` picks a different partition (uniform random among the others).
  Keyed records: `partitioner.ForKey`. Explicit `Record.Partition >= 0` is used as is.
- **Retries (FR12)**: for each batch: send to the current leader with `leader_epoch` from the cache;
  on a retriable error (§1.1) invalidate/refresh metadata as needed, sleep `backoff(attempt)` (via a
  timer that also selects on the producer's close-abort channel) and retry, until
  `DeliveryTimeout` from the batch's creation; then fail all its records with the last error.
  Non-retriable errors fail immediately. acks=none: one attempt, callbacks get offset −1.
- **Backpressure**: `BufferMemory` is a weighted semaphore (bytes); `Produce` blocks until room or
  ctx done. Released when a batch completes.
- **Shutdown**: `Close` = mark closed, seal all open batches, close queues, wait for senders (each
  finishes its queue with normal retry semantics, bounded by DeliveryTimeout or ctx), then stop.
  If ctx expires, remaining batches fail with `ErrProducerClosed` and senders exit. Goroutines:
  one sender per partition used, owned by the Producer, joined in Close (goleak-clean).
- Lock ordering: `Producer.mu` (partition map, closed flag) → `partitionState.mu` (open batch).

## 3. Consumer (`consumer.go`) — standalone

```go
type OffsetReset int // ResetEarliest, ResetLatest (default)
type ConsumerConfig struct { MaxWait time.Duration /* 500ms */; MinBytes int /* 1 */;
    MaxBytes int /* 16 MiB */; MaxPartitionBytes int /* 1 MiB */; AutoOffsetReset OffsetReset }
func NewConsumer(c *Client, cfg ConsumerConfig) (*Consumer, error)
func (c *Consumer) Assign(tps []TopicPartition)        // replaces the assignment; positions unset
func (c *Consumer) Assignment() []TopicPartition
func (c *Consumer) Seek(tp TopicPartition, offset int64) error
func (c *Consumer) SeekToBeginning(ctx, tps ...TopicPartition) error / SeekToEnd(ctx, tps...)
func (c *Consumer) Position(tp TopicPartition) (int64, bool)
func (c *Consumer) Poll(ctx) ([]Record, error)
func (c *Consumer) Close() error
```
`Poll`: resolve unset positions via `ListOffsets` (auto reset policy); group assigned partitions by
leader; one Fetch per leader (sequentially; single node = one request) with each partition's
cached epoch; decode, **drop records below the position** (a fetch returns whole batches), advance
positions. Per-partition errors: NOT_LEADER/FENCED/UNKNOWN → invalidate + refresh, skipped this poll;
OFFSET_OUT_OF_RANGE → reset per policy; others returned as error. Not safe for concurrent use
(documented, like Kafka's consumer); `Close` is idempotent.

## 4. Admin (`admin.go`)
```go
func NewAdmin(c *Client) *Admin
func (a *Admin) CreateTopic(ctx, name string, partitions, rf int32, configs map[string]string) error
func (a *Admin) DeleteTopic(ctx, name string) error
func (a *Admin) ListTopics(ctx) ([]string, error)
func (a *Admin) DescribeTopics(ctx, names ...string) ([]TopicDescription, error)
func (a *Admin) ListOffsets(ctx, tp TopicPartition, timestamp int64) (int64, error) // -2/-1/ts
type TopicDescription struct { Name string; Configs map[string]string; Partitions []PartitionDescription }
type PartitionDescription struct { Partition, Leader, LeaderEpoch int32; Replicas, ISR []int32 }
```
Admin calls go to any broker; error codes become `ServerError`s. Transport errors are retried with
backoff up to `RequestTimeout`-bounded ctx (create/delete are not blindly retried after a
transport error that may have succeeded: on retry, TOPIC_ALREADY_EXISTS after a prior transport
error is reported as success only if the topic exists with the requested partition count —
documented).

## 7. Tests (all goleak-clean, no sleeps, testify)
Fake server for unit tests: `pkg/client/fake_test.go` — a `StreamQServiceServer` on `bufconn`
whose Produce/Fetch/Metadata/ListOffsets behaviour is scripted per call (queue of responses or
`func`s), recording requests.
- **errors/backoff**: code → sentinel table; `IsRetriable` table; backoff bounds with fixed rand.
- **metadata**: cache hit avoids RPC; invalidate + refresh; bootstrap failover to the second address
  when the first is down; concurrent refreshes coalesce (count RPCs).
- **producer**:
  - batching: `BatchSize` seals (several batches), `Linger` seals (manual timer via a fake
    `Linger` large + `Flush`), per-partition order of callbacks;
  - keyed records land in `ForKey` partitions; unkeyed sticky: all records of one batch share a
    partition, the next batch switches;
  - **retry on injected errors** (§9): NOT_LEADER ×2 then success → one metadata refresh per
    failure, records acked once with correct offsets; gRPC Unavailable ×2 then success;
    NOT_ENOUGH_REPLICAS retried; MESSAGE_TOO_LARGE not retried (callback error, one attempt);
    DeliveryTimeout exhaustion → callbacks fail with the last error; backoff uses jitter source;
  - ordering under retries: batch 1 fails twice while batch 2 is queued → server sees 1 before 2;
  - **Close flushes** (§9): records produced with a long Linger are delivered and every callback
    has run when `Close` returns; `Produce` after Close → `ErrProducerClosed`; Close with expired
    ctx fails pending callbacks;
  - BufferMemory blocks until a batch completes; ctx cancel unblocks.
- **consumer**: assign + poll from earliest/latest; mid-batch position drops earlier records;
  NOT_LEADER → refresh then continue; OFFSET_OUT_OF_RANGE → reset; Seek/Position.
- **admin**: each call maps request/response and error codes.
- **integration (real broker, `internal/node` in-process)**: producer + consumer round trip of 10k
  keyed records across 4 partitions with per-key order, and the examples' tests.

## Revision 1 (after plan-review round 1)

These rules supersede anything above that conflicts with them.

- **R1 (finding 1) Partition selection**: drop `AnyPartition`. `Record` gains
  `UsePartition bool`. When producing, `Partition` is honored only if `UsePartition` is true;
  otherwise the partitioner chooses (murmur2 for keys, sticky for none). Consumed records have
  `Partition` set (and `UsePartition` true). An explicit partition ≥ the partition count fails the
  record's callback with `ErrUnknownTopicOrPartition`. Tests: a zero-value keyed record lands in
  `ForKey(key, n)`; an out-of-range explicit partition fails.
- **R2 (finding 2) Producer concurrency design**:
  - Each partition's sealed batches live in a mutex-guarded slice with a 1-buffered signal
    channel. The queue is never closed; per-partition `closed` flags are set under
    `partitionState.mu`.
  - `Produce` acquires buffer bytes with a ctx merged from the caller's ctx and the producer's
    `closing` channel, so `Close` unblocks it with `ErrProducerClosed`. After acquiring, it
    re-checks `closed` under `partitionState.mu`; if the producer is closed it releases the bytes
    and fails.
  - The linger timer callback takes `partitionState.mu` and acts only if the open batch's
    generation still matches and the state isn't closed.
  - A record whose encoded size is larger than `BufferMemory` or `MaxRequestSize` is rejected
    synchronously (`ErrMessageTooLarge`).
  - Race test: N goroutines call `Produce` while `Close` runs. Every accepted record's callback
    runs exactly once, rejected calls return an error, and nothing panics.
- **R3 (finding 3) Locks**:
  - Order: `Producer.mu` → `partitionState.mu`. The partitioner's own mutex is a leaf.
  - The default partitioner keeps sticky state internally under its mutex. `OnNewBatch` and
    `Partition` are called **without** any producer lock held: sealing records which partition it
    sealed, and the hook runs after unlock.
  - `Producer.mu` is never held while blocking on the semaphore, metadata or a queue.
  - Documented in `doc.go`.
- **R4 (finding 4) Message size**:
  - New `ProducerConfig.MaxRequestSize` (default 1 MiB) replaces the hard-coded guard.
  - Sealing size = `min(BatchSize, MaxRequestSize, topic max_message_bytes if overridden in
    metadata configs)`.
  - On `MESSAGE_TOO_LARGE` for a batch of more than one record, the sender splits it in half and
    puts both halves back at the head of the queue, keeping order (one in flight; Kafka
    `splitAndReenqueue`). Single-record batches fail.
  - Tests: a topic limit of 2 KiB with 10 × 500 B records all succeed in order; a single 4 KiB
    record fails with `ErrMessageTooLarge`.
- **R5 (finding 5) Split changed**: the **Producer is built by the main session** (its locking
  is subtle and tightly coupled). Only package **B (Consumer + Admin)** goes to an implementer.
  - The core commit also includes `serverError` (code + msg → error), header conversions
    (`toRecordHeaders`/`fromRecordHeaders` in `record.go`), the fake cluster/broker in
    `fake_test.go` (scriptable overrides plus `singleBroker`), and `record.EncodedRecordSize` in
    `internal/record`, which the main session adds.
  - B's new package-level identifiers live in its own files with a `consumer`/`admin` prefix, or
    are methods.
  - After the merge: `go build ./... && make lint test` before examples and integration.
- **R6 (finding 6) Clock**: the Producer takes an internal `clock` interface (`Now`,
  `AfterFunc(d, f) (stop func() bool)`, `NewTimer(d) (C, stop)`) used for linger, retry backoff
  and delivery deadlines. Tests use a fake clock: with Linger 50 ms and a huge BatchSize, nothing
  is sent until the fake clock advances, then the batch is sent without a Flush.
- **R7 (finding 7) Consumer fairness**: after a partition error the partition is excluded from
  fetches for `backoff(attempt)` (attempts reset on success). The partition order rotates every
  poll. Test: a partition that keeps returning UNKNOWN doesn't make `Poll` return early for the
  healthy ones (the fake asserts the excluded partition is absent from the next fetch).
- **R8 (finding 8)** `ResourceExhausted` is not retriable.
- **R9 (finding 9) Timeouts**:
  - Produce sends `timeout_ms = RequestTimeout`. The RPC ctx deadline is RequestTimeout + 1 s,
    derived from the producer's abort ctx, so `Close` with an expired ctx cancels in-flight RPCs.
  - `NewProducer` validates `DeliveryTimeout ≥ Linger + RequestTimeout`.
- **R10 (finding 10) Edge cases**:
  - Unknown topic (D23): `Produce` waits for the topic's metadata, refreshing with backoff,
    bounded by ctx and `ProducerConfig.MaxBlock` (default 60 s, Kafka `max.block.ms`). After that
    it returns `ErrUnknownTopicOrPartition` synchronously.
  - A timestamp before the Unix epoch is rejected synchronously (`ErrInvalidTimestamp`, D9).
  - Batches use `BuilderOptions{ProducerID: NoProducerID, ProducerEpoch: 0, BaseSequence:
    NoSequence}` (SPEC: epoch 0 for now).
  - A batch already past DeliveryTimeout when it reaches the head of the queue fails without
    being sent.
  - A response missing the requested partition counts as retriable.
  - Leader −1 gives `ErrNotLeader` (retriable).
  - Calling `Flush`/`Close`/`ProduceSync` from a callback deadlocks (documented).
  - `Client.Close` comes after `Producer.Close` and is idempotent (documented).
- **R11 (finding 11) Lint** Sentinels are `errors.New`, codes are mapped with a `switch`
  (already done), and the rand constructors carry `//nolint:gosec // G404: ...`.
- **R12 (finding 12) Coalescing** stays hand-rolled (no new import needed). The test waits until
  all N callers are registered as waiters on the in-flight call (internal counter), then releases
  the fake and asserts exactly 1 Metadata RPC.
- **R13 (finding 13)** Examples create topics with RF 1 and `min_insync_replicas=1` (or flags).
  Admin's create retry with `partitions <= 0` accepts any existing count.
- **R14 (finding 14)** Test: FENCED_LEADER_EPOCH once triggers a refresh, and the retry carries
  the new epoch from metadata (asserted on the request's `leader_epoch`).

### Decisions added
- D23 Producing to an unknown topic waits for metadata up to `min(ctx, MaxBlock=60s)`, then fails
  with `ErrUnknownTopicOrPartition` (Kafka `max.block.ms`). This answers the reviewer's question.
- D24 A batch rejected with MESSAGE_TOO_LARGE is split and re-queued (Kafka); only single-record
  batches fail.

## Implementation notes (deviations recorded during code review)

- An explicit `Partition` outside the topic's range is rejected **synchronously** by `Produce`
  (`ErrUnknownTopicOrPartition`), not through the callback (R1). This is consistent with the other
  synchronous validation errors in `Produce`, and the record is never accepted.
- `internal/testnode` is a test-only helper package (it imports `testing` and testify). Production
  code must never import it.
- Sticky records use Kafka's `abortOnNewBatch`: a record that would start a new batch is
  re-partitioned once after the partitioner moves on.
- Shared metadata refreshes run in a client-owned goroutine under the Client's lifetime context,
  so a caller's cancellation never fails the other callers (code-review round 1, MAJOR).
