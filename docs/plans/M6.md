# M6 — Replication (plan)

SPEC refs: §3.1 (leader-epoch-checkpoint), §4 (all: pull replication, LEO/HW, ISR shrink/expand via
AlterISR with epoch checks, election rule, leader-epoch cache, OffsetForLeaderEpoch truncation,
stale-epoch fencing, acks semantics and purgatory), §7.2 (ReplicaFetch, OffsetForLeaderEpoch,
AlterISR), §8 FR4, FR8, §9 M6.
Acceptance (§9): kill the leader during continuous `acks=all` produce → zero acknowledged records
lost; a restarted follower catches up and rejoins the ISR; a deliberately divergent follower log is
truncated; `NOT_ENOUGH_REPLICAS` when ISR < min.insync.

CLAUDE.md: the core of M6 (replication, HW, ISR, truncation) is built **by the main session
alone** — no implementer split this milestone.

Out of scope: idempotent producer state on followers (M7), controlled shutdown (M8), unclean
election (never), rack awareness, follower fetching by consumers, reassignment.

## 1. Storage additions (`internal/storage`)
- `Log.AppendAsFollower(ctx, b record.Batch) (AppendInfo, error)` — validates the batch (CRC,
  canonical) and requires `b.BaseOffset() == LEO` (else `ErrOffsetMismatch`, new sentinel); offsets
  and leader epoch are kept as sent by the leader; same roll/flush/failure semantics as `Append`.
- `Log.TruncateTo(ctx, offset int64) error` — removes every record with offset ≥ `offset` (no-op if
  `offset >= LEO`; `ErrOffsetOutOfRange` if `offset < logStartOffset`): segments whose base ≥ offset
  are closed and deleted (directly, not delayed: only followers truncate and followers serve no
  consumer reads); the segment containing `offset` is cut at the start of the batch containing it
  — the follower always truncates at batch boundaries because leader end offsets are batch
  boundaries — via `segment.truncateTo`: file truncate + fsync, both indexes `truncateTo`, size/
  nextOffset/maxTimestamp recomputed (rescan of the remaining tail from the last index entry);
  LEO and `recoveryPoint = min(recoveryPoint, offset)` updated; then the dir is fsynced. Runs under
  `Log.mu`; readers racing a truncation on a follower are not a correctness concern (they get
  data that will be re-fetched or an error), documented.
- `segment` gains `lastEpoch`-agnostic helpers only; no format change.

## 2. Leader-epoch cache (`internal/partition/epochcache.go`)
```go
type EpochCache struct { mu; entries []storage.EpochEntry; path string }  // ascending epochs/offsets
func OpenEpochCache(ctx, dir string) (*EpochCache, error)   // reads leader-epoch-checkpoint
func (c *EpochCache) Assign(ctx, epoch int32, startOffset int64) error
    // ignored if epoch <= last epoch; else append (and drop entries with startOffset >= this one,
    // which cannot happen in a consistent log); persisted (atomic checkpoint write) on change
func (c *EpochCache) LatestEpoch() (int32, bool)
func (c *EpochCache) EndOffsetFor(epoch int32, leo int64) (int32, int64)
    // Kafka semantics: the largest cached epoch <= epoch, and its end offset = start offset of the
    // next cached epoch, or leo if it is the latest; (-1, -1) if epoch is below every entry
func (c *EpochCache) TruncateFromEnd(ctx, offset int64) error   // drop entries with start >= offset
func (c *EpochCache) TruncateFromStart(ctx, offset int64) error // retention: entries fully below
    // offset collapse into one entry starting at offset
```
The partition keeps the cache consistent with the log: the leader assigns `(newEpoch, LEO)` in
`BecomeLeader`; followers assign `(batch.LeaderEpoch, batch.BaseOffset)` for every appended batch
whose epoch is newer; truncation truncates the cache too; on open, the cache is truncated to the
recovered LEO (a crash may leave the log shorter than the checkpoint).

## 3. Partition (leader side)
State added: `followers map[int32]*followerState{leo int64; lastFetch, lastCaughtUp time.Time}`,
`epochs *EpochCache`, `leoCh` (closed/replaced on LEO advance, for replica long-polls),
`pendingISR` (one AlterISR in flight), injected clock.
- `HandleReplicaFetch(ctx, replicaID, requestEpoch, fetchOffset, maxBytes) (ReplicaFetchResult, error)`:
  epoch check (FENCED / NOT_LEADER); `replicaID` must be a replica (else NOT_LEADER-ish error
  `ErrNotReplica`); records `follower.leo = fetchOffset` (a follower fetches from its LEO), sets
  `lastCaughtUp = now` if `fetchOffset >= leaderLEO` observed at this fetch (Kafka's rule using the
  LEO at the previous fetch: `fetchOffset >= lastFetchLeaderLEO`); recomputes HW =
  **min LEO over the current ISR** (leader's LEO included) — HW never decreases; maybe expands ISR
  (§3.2); reads `Log.Read(fetchOffset, maxBytes, maxOffset = LEO)`. `fetchOffset > LEO` →
  OFFSET_OUT_OF_RANGE; `< logStart` → OFFSET_OUT_OF_RANGE with logStart in the result.
- `HW`: `advanceHWLocked` becomes min over ISR members' LEOs (unknown follower LEO → HW does not
  advance past the HW already established); after HW moves, `hwCh` wakes produce waiters and
  consumer long-polls.
- **acks=all purgatory** (§4.5): `Append` with acks=all checks ISR size ≥ min.insync **before**
  appending (`ErrNotEnoughReplicas`), appends, then the produce handler waits on `HWChanged()`
  until `HW > lastOffset` (success), the request timeout (`ErrRequestTimedOut`, data may still
  commit), leadership loss (`ErrNotLeader`), or ctx — capture-then-check, no polling. One
  goroutine per waiting request is the gRPC handler goroutine itself (no extra goroutines).
- **ISR shrink** (§4.3): a per-broker `isrLoop` (one goroutine owned by the broker, ticker
  `replica_lag_max_ms/2`, injected clock) asks every led partition `MaybeShrinkISR(now)`: ISR
  members (other than the leader) with `now - lastCaughtUp > replica_lag_max_ms` are removed via
  AlterISR.
- **ISR expand**: in `HandleReplicaFetch`, a non-ISR replica whose LEO ≥ HW and ≥ the start offset
  of the leader's current epoch (Kafka KIP-841 rule, so a follower that has not reached the current
  epoch is not added) is added via AlterISR.
- **AlterISR**: `alterISR(newISR)` sends `AlterISR{topic, partition, leader_id, leader_epoch,
  partition_epoch, new_isr}` to the controller's internal API; at most one in flight per partition;
  the leader **keeps using its current ISR until the change arrives through metadata**
  (`PartitionChanged` → `ApplyState`, which also clears `pendingISR`); errors (FENCED / NOT_CONTROLLER
  / transport) clear `pendingISR` so the next fetch/tick retries. Sent from a per-partition async
  goroutine owned by the broker's errgroup (bounded: one per partition at a time).

## 4. Partition (follower side) — replica fetcher (`internal/broker/fetcher.go`)
`BecomeFollower(leader, epoch)` (re)starts the partition's fetcher (one goroutine per followed
partition, owned by the broker; old fetcher cancelled and joined first). Loop:
1. **Truncate** (§4.4): `lastEpoch := epochs.LatestEpoch()`; if present call leader
   `OffsetForLeaderEpoch(topic, partition, current leader_epoch, lastEpoch)` → `(epoch, endOffset)`;
   truncate log + epoch cache to `min(LEO, endOffset)` (if the leader returns an epoch < lastEpoch,
   also truncate cache entries after it). If no epoch is cached, truncate to the local HW (Kafka's
   fallback) — only possible for a log without data.
2. **Fetch** repeatedly: `ReplicaFetch(replica_id=self, leader_epoch, fetch_offset=LEO,
   max_bytes=1MiB, max_wait_ms=500)`; append each batch with `AppendAsFollower` (and
   `epochs.Assign` for new epochs); follower HW = `min(leaderHW, LEO)`; notify followers' HW waiters.
   Errors: FENCED_LEADER_EPOCH / NOT_LEADER → wait for the next metadata change (the fetcher exits;
   ApplyState restarts it); OFFSET_OUT_OF_RANGE with fetch offset < leader log start → truncate
   fully and restart at the leader's log start (`TruncateFullyAndStartAt`, storage helper);
   otherwise (fetch offset > leader LEO, i.e. diverged) → back to step 1; transport errors → backoff
   and retry. Exits on ctx cancel (partition no longer followed / broker closing).

## 5. Metadata & controller
- New command `AlterISRCommand{topic, partition, leader_epoch, partition_epoch, new_isr}`
  (internal.proto oneof 16). FSM: topic/partition must exist; `leader_epoch` and `partition_epoch`
  must equal the current ones (else `ErrFencedLeaderEpoch`, new metadata sentinel → FENCED_LEADER_EPOCH);
  new ISR non-empty, ⊆ replicas, contains the leader, every member unfenced except possibly the
  leader; applies, `partition_epoch++`, emits PartitionChanged. Term-bound like other controller
  commands.
- Internal RPCs (internal.proto, additive): `ReplicaFetch`, `OffsetForLeaderEpoch`, `AlterISR`.
  ```proto
  message ReplicaFetchRequest { int32 replica_id = 1; string topic = 2; int32 partition = 3;
    int32 leader_epoch = 4; int64 fetch_offset = 5; int32 max_bytes = 6; int32 max_wait_ms = 7; }
  message ReplicaFetchResponse { ErrorCode error_code = 1; string error_message = 2;
    int64 high_watermark = 3; int64 log_start_offset = 4; int64 log_end_offset = 5; bytes records = 6; }
  message OffsetForLeaderEpochRequest { string topic = 1; int32 partition = 2;
    int32 current_leader_epoch = 3; int32 requested_epoch = 4; }
  message OffsetForLeaderEpochResponse { ErrorCode error_code = 1; string error_message = 2;
    int32 leader_epoch = 3; int64 end_offset = 4; }
  message AlterISRRequest { int32 leader_id = 1; string topic = 2; int32 partition = 3;
    int32 leader_epoch = 4; int32 partition_epoch = 5; repeated int32 new_isr = 6; }
  message AlterISRResponse { ErrorCode error_code = 1; string error_message = 2; int32 controller_id = 3; }
  ```
  One RPC per partition (simple; batching per broker is a later optimisation, noted).
- The controller handles AlterISR (leader-only apply, term-stamped).

## 6. Broker wiring
- Partitions now open with a leader-epoch cache; `ApplyState` → `BecomeLeader` (cache assign,
  follower state reset, stop fetcher) / `BecomeFollower` (start fetcher); ISR-only updates as M5.
- `internal/server/internal.go` serves ReplicaFetch / OffsetForLeaderEpoch (via the broker) and
  AlterISR (via the controller).
- Produce handler: acks=all waits per §3; `timeout_ms` bounds the wait (default 30 s if 0).
- HW checkpoint covers followers too; epoch checkpoints are per partition dir.
- Consumers: Fetch remains leader-only and bounded by HW (FR4).

## 7. Tests
- **storage**: AppendAsFollower (offset mismatch rejected, batches kept as-is), TruncateTo table
  (inside last segment at a batch boundary, at a segment base, across several segments, no-op,
  below log start), reopen after truncation (recovery consistent), indexes valid after truncation
  (every surviving offset readable), recovery point clamped.
- **epoch cache**: Assign/EndOffsetFor (Kafka cases: exact, between, below first, latest = LEO),
  TruncateFromEnd/Start, persistence round trip, open truncated to LEO.
- **partition leader**: HW = min over ISR; HW never decreases; replica fetch updates follower LEO /
  caught-up time; expand rule (LEO ≥ HW and ≥ current-epoch start) triggers one AlterISR; shrink
  after lag (fake clock) triggers one AlterISR; ISR used until metadata confirms; acks=all wait:
  success when HW passes, REQUEST_TIMED_OUT after timeout (fake clock via short real ctx where
  needed), NOT_ENOUGH_REPLICAS before append, NOT_LEADER on leadership loss while waiting.
- **fetcher / truncation** (two in-process partitions wired by a fake leader client): follower
  catches up from empty; **divergent follower**: follower log has extra batches at an old epoch
  (written directly with AppendAsFollower), leader at a new epoch → OffsetForLeaderEpoch truncates
  the follower to the divergence point, then it fetches the leader's records; out-of-range below
  log start → truncate fully; FENCED → fetcher exits.
- **FSM**: AlterISR table (stale epochs rejected, invalid ISRs rejected, epoch bump).
- **Integration (§9)** `test/integration/replication_test.go` (3-node cluster, RF 3, min.insync 2,
  replica lag 2 s, session 2 s):
  1. **No acked loss on leader kill**: a producer (client lib, acks=all, retries) writes
     continuously (sequence-numbered values) to a partition; mid-stream the partition leader's node
     is closed; production continues against the new leader; afterwards every acknowledged value
     is present in the partition (consumed from the new leader up to HW); duplicates allowed
     (at-least-once until M7), order per key preserved for acked values.
  2. **Restarted follower catches up and rejoins ISR**: stop a follower, produce more, restart it;
     `require.Eventually` its LEO = leader LEO and it is back in the ISR (Metadata).
  3. **Divergent follower truncation** at cluster level: covered by the fetcher unit test (precise
     control); the cluster test additionally restarts the old leader (which may hold an unacked
     tail) and checks all three replicas converge to identical logs (compare batches byte-wise).
  4. **NOT_ENOUGH_REPLICAS**: stop two of three brokers; after the ISR shrinks to the leader,
     acks=all produce returns NOT_ENOUGH_REPLICAS and nothing is appended.

## 8. Decisions
- D39 Truncation deletes segments immediately on followers (no delayed delete): followers serve
  no consumer reads; documented risk: a replica fetch from a just-demoted leader racing truncation
  can return data that is then truncated — harmless because the fetching follower re-truncates
  via OffsetForLeaderEpoch on its next leader change.
- D40 HW follows Kafka: min LEO over the ISR, never decreasing; follower HW = min(leader HW, LEO).
- D41 ISR expand requires LEO ≥ HW and ≥ the leader's current-epoch start offset (KIP-841).
- D42 One fetcher goroutine per followed partition and one RPC per partition (simplicity over
  per-broker batching); AlterISR one-in-flight per partition.
- D43 acks=all waiting happens on the handler goroutine on the partition's HW channel (the
  "purgatory"); produce `timeout_ms` 0 → 30 s.

## Revision 1 (after plan-review round 1)

These rules supersede anything above that conflicts with them. (Plan-independent storage and
epoch-cache code was drafted in the working tree before approval. It is uncommitted and follows
these rules.)

- **R1 (BLOCKER 1) Maximal ISR (Kafka KIP-497)**: the leader keeps `committedISR` (from
  metadata) and `pending` (an in-flight AlterISR).
  - HW = min LEO over the **maximal ISR** = committed ISR ∪ pending additions. Members a pending
    shrink would remove are still counted until the shrink is committed.
  - min.insync checks use the **committed** ISR only.
  - `pending` is cleared only by a definitive FSM rejection (FENCED_LEADER_EPOCH / invalid ISR →
    re-evaluate next time) or by `ApplyState` with a newer `partition_epoch`.
  - On transport errors or unknown outcomes the **same** request is retried (backoff), never
    dropped.
  - Unit test: with an expand in flight, the HW never passes the pending member's LEO.
- **R2 (BLOCKER 2) acks=all tied to the leader epoch**:
  - `Append` returns the leader epoch it appended under.
  - The produce wait succeeds only if, under `p.mu`, `isLeader && leaderEpoch == appendEpoch &&
    HW > lastOffset`, plus R9. If leadership or epoch changed it returns `ErrNotLeader`.
  - `BecomeLeader`/`BecomeFollower` close a `stateCh` (closed and replaced on every leadership
    transition) that waiters also select on.
  - Test: an acks=all waiter, then BecomeFollower, truncation and a follower HW advance → NOT_LEADER,
    never success.
- **R3 (BLOCKER 3) Fetcher retries, never self-exits**: the fetcher exits only when its ctx is
  cancelled. On NOT_LEADER, FENCED_LEADER_EPOCH, an unknown leader or transport errors it backs
  off (injected clock, 50 ms → 1 s) and retries with the epoch it holds. A newer metadata change
  replaces it. The same applies to OffsetForLeaderEpoch. Unit test: the leader answers NOT_LEADER
  twice, then succeeds.
- **R4 (BLOCKER 4) NOT_ENOUGH_REPLICAS test keeps quorum**: a topic with RF 3 and
  min.insync 3; stop **one** non-leader broker. `require.Eventually` the ISR (Metadata) shrinks to
  2, then acks=all produce returns NOT_ENOUGH_REPLICAS and the leader's LEO is unchanged. A unit
  test covers it too.
- **R5 (MAJOR 5) Kafka's caught-up rule, exactly**:
  - On each fetch from follower f:
    - if `fetchOffset >= current LEO`, then `lastCaughtUp = now`;
    - else if `fetchOffset >= f.lastFetchLeaderLEO`, then `lastCaughtUp = f.lastFetchTime`.
  - Then `f.lastFetchLeaderLEO = current LEO` and `f.lastFetchTime = now`.
  - On BecomeLeader every follower resets to LEO unknown (-1) and `lastCaughtUp = now`.
  - Test: steady appends with fetches trailing by one batch never shrink the ISR. A stalled
    follower shrinks after `replica_lag_max_ms`.
- **R6 (MAJOR 6) KIP-279 truncation**: the follower sends `OffsetForLeaderEpoch(latestEpoch)`.
  - Reply `(E', end)`:
    - if `E' == latestEpoch`, truncate to `min(LEO, end)`;
    - if `E' < latestEpoch`, truncate to `min(LEO, end, localEndFor(E'))`, where `localEndFor` is
      the follower's own `EndOffsetFor(E')`, then repeat with the new latest epoch until they match.
  - Reply `(-1, -1)`: truncate to the local HW.
  - A target below the local log start uses `TruncateFullyAndStartAt(leaderLogStart)`.
  - No cached epoch (pre-M6 data, or a lost checkpoint) also truncates to the local HW (Kafka's
    fallback); the earlier claim that this only happens without data is withdrawn.
  - A lowering setter `Partition.truncateHW(newLEO)` sets HW = min(HW, LEO) after truncation, and
    is used only there (FR4).
  - Unit test: follower epochs [(0,0),(2,10)] against leader epochs [(0,0),(1,8),(3,20)] converge
    to an identical log.
- **R7 (MAJOR 7) Truncation durability**:
  - `TruncateTo` deletes segments **newest-first** with a dir fsync after each, then cuts the
    containing segment (fsync).
  - The caller (partition) then **synchronously** writes the recovery-point checkpoint via
    `Manager.CheckpointRecoveryPoints` before any further append. The epoch-cache truncation is
    persisted before appending.
  - Followers persist `Assign(newEpoch, base)` before appending a batch that starts a new epoch.
  - Leaders persist `Assign(newEpoch, LEO)` in BecomeLeader before accepting appends.
  - Test: truncate, append without flushing, then reopen with the old checkpoint file contents
    restored. The log opens with no ErrCorruptLog.
- **R8 (MAJOR 8) Fetcher lifecycle (broker-driven)**:
  - `Partition.ApplyState` returns the transition (none / ISR-only / becameLeader /
    becameFollower) instead of acting on fetchers.
  - The broker (under `applyMu`, holding no partition lock) stops and joins the old fetcher, then
    calls `BecomeLeader` or `BecomeFollower`, then starts the new fetcher.
  - Follower appends go through `Partition.AppendAsFollower(fetchEpoch, batch)`, which checks
    `!isLeader && leaderEpoch == fetchEpoch` under `p.mu`; a stale fetcher's write is refused.
  - Fetchers and AlterISR goroutines are stopped and joined before `DeleteLog`/`deleteTopic`,
    before `resync` deletions, and in `Broker.Close` before `mgr.Close`.
  - The run ctx and goroutine group are created **before** `applySnapshot` in `broker.Open`.
  - Fetcher and AlterISR goroutines use a `sync.WaitGroup` per partition (not errgroup); they log
    errors and never cancel siblings.
  - Lock order is documented at the top of partition.go and fetcher.go:
    `Broker.applyMu → Partition.mu → (storage) → Partition.hwMu`. The fetcher holds no partition
    lock while blocked on RPCs.
  - goleak tests: delete-while-following and close-while-following.
- **R9 (MAJOR 9) NOT_ENOUGH_REPLICAS after append**: when the HW passes the record, the produce
  wait also requires `len(committedISR) >= minInsync`. Otherwise it returns `ErrNotEnoughReplicas`
  (retriable; the data may still commit). This mirrors Kafka's
  NOT_ENOUGH_REPLICAS_AFTER_APPEND, mapped to NOT_ENOUGH_REPLICAS (D44). Unit test included.
- **R10 (minor 10)** Retention is bounded by each partition's HW (a limit func passed by the
  broker). The epoch cache's `TruncateFromStart(logStart)` runs after retention and on open.
- **R11 (minor 11)** The leader skips expanding brokers that are fenced in its local metadata, and
  the controller validates before proposing.
- **R12 (minor 12) Replica-fetch details**:
  - A non-replica's fetch gets NOT_LEADER.
  - `follower.leo` is updated only after validating `fetchOffset ≤ LEO`.
  - `leoCh` is also closed on leadership transitions and shutdown, so replica long-polls end
    promptly.
  - `ReplicaFetchRequest` gains `int64 broker_epoch = 8`. The leader checks it against its local
    metadata's broker epoch (when known) and rejects stale incarnations with STALE_BROKER_EPOCH
    (KIP-903).
- **R13 (minor 13) Purgatory timing**:
  - The wait uses the injected clock's `After(min(timeout_ms or 30 s, ctx deadline − 100 ms))`.
  - Unit tests advance the fake clock.
  - The default produce `timeout_ms` from `pkg/client` stays the request timeout. The server bound
    is slightly below the RPC deadline, so clients see REQUEST_TIMED_OUT.
- **R14 (minor 14)** Segment truncation rescans the **whole remaining segment's** batch headers,
  not just the tail, for maxTimestamp, the first-batch timestamp and bytes since the last index
  entry; an empty segment resets them. The cut segment always stays the active segment, so a cut
  at the first segment's base leaves one empty active segment. Covered in the TruncateTo table.
- **R15 (minor 15)** The M5 interim guard (refusing acks=all when the ISR has followers) and its
  test assertion are removed and replaced by R1/R2/R9. The PROGRESS_LOG limitation is updated.
- **R16 (minor 16) Integration test 1 strengthened**:
  - It requires ≥ 100 acknowledged records **after** the new leader appears in Metadata.
  - After the run, all live replicas reach the same LEO and HW, with byte-identical batches up to
    the HW (each broker's local log is read through `testnode` cluster access).

### Decisions added
- D44 NOT_ENOUGH_REPLICAS is also returned after the append when the committed ISR dropped below
  min.insync before the HW reached the record (Kafka's NOT_ENOUGH_REPLICAS_AFTER_APPEND, mapped to
  the §7.3 code).
- D45 HW uses the maximal ISR (committed ∪ pending additions), and min.insync uses the committed
  ISR (KIP-497).
- D46 Follower truncation follows KIP-279: iterate OffsetForLeaderEpoch until the epochs match,
  falling back to the HW when there is no epoch information.

## Revision 2 (after plan-review round 2)

- **R17 (MAJOR 1) Keep pending on FENCED (Kafka)**:
  - A FENCED_LEADER_EPOCH reply to AlterISR (a leader or partition epoch mismatch) **stops
    retrying but keeps `pending`**. The leader keeps computing the HW over the maximal ISR, because
    the rejection proves newer partition state exists, which may already contain the change.
  - `pending` is cleared only when `ApplyState` delivers a newer partition epoch or leader epoch, or
    when the FSM rejects the ISR's **content** at a matching epoch (`ErrInvalidISR`: non-replica or
    fenced member). State is unchanged in that case.
  - Unit test: the expand commits, the response is lost (transport error), and the retry gets
    FENCED. The HW must not pass F2's LEO until the metadata update arrives.
- **R18 (minor 2) Broker-epoch check**:
  - A ReplicaFetch is rejected with STALE_BROKER_EPOCH only when the request epoch is **lower**
    than the follower's epoch in the leader's local metadata. Greater epochs are accepted, since
    the leader's metadata may lag a re-registration.
  - `node` passes its registration epoch to the broker via `Broker.SetBrokerEpoch(epoch)` (atomic)
    on every (re-)registration, and fetchers read it per request.
  - Single-node mode uses 0, and the check is skipped there.
- **R19 (minor 3)** `OffsetForLeaderEpochResponse` gains `int64 log_start_offset = 5`, which the
  follower uses for the `TruncateFullyAndStartAt(leaderLogStart)` fallback.
- **R20 (minor 4)** The fetcher (internal/broker, which holds the Manager) calls
  `Manager.CheckpointRecoveryPoints` synchronously after `TruncateTo` or `TruncateFullyAndStartAt`
  returns, and before the next AppendAsFollower, for both truncation paths.
