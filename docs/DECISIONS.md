# Design Decisions

Decisions not dictated by `docs/SPEC.md`. One entry per decision, newest last.

---

## D1. Proto layout: `api/v1/` directory, `streamq.v1` package (M0)

The required repository layout puts protos in `api/v1/*.proto`, with `buf.yaml` declaring a
single module at `api`. buf's `STANDARD` lint wants the proto package to match the directory
relative to the module root (which would be just `v1`), but a bare `v1` package is a poor wire
identifier. We use `package streamq.v1;` and disable only `PACKAGE_DIRECTORY_MATCH`. Go code is
generated by buf managed mode (`go_package_prefix: github.com/sudo-ss1/streamq/gen`) into `gen/v1/`
with Go package name `streamqv1`. Generated code is committed, and CI fails if `make gen` changes it.

## D2. Pinned, project-local dev tools (M0)

buf, golangci-lint, protoc-gen-go and protoc-gen-go-grpc are installed at exact versions into
`.tools/bin` by `make tools`, not added to `go.mod` as tool dependencies, so the module graph
contains only runtime and test dependencies. Versions are pinned in the `Makefile`; the
golangci-lint version is duplicated in `.github/workflows/ci.yml` (which uses the official action)
and must be bumped in both places.

## D3. Index file format and validity (M1)

Offset index entries are 8 bytes big-endian `(relativeOffset uint32, position uint32)` and map a
batch's **baseOffset** to its file position. Time index entries are 12 bytes big-endian
`(timestamp int64, relativeOffset uint32)`, where the timestamp is the largest batch maxTimestamp
seen so far in the segment and the offset is the baseOffset of the batch where that maximum was
first seen. Before a batch is written, both indexes get an entry if at least
`index.interval.bytes` were written since the last one, so position 0 is never indexed. A time
entry is written only if its timestamp is greater than the last one's and it is not all-zero.
Index files are preallocated (sparse) to `MaxIndexBytes` (10 MiB, rounded down to the entry size)
and trimmed on roll and close. On open, the valid entries are the leading run of entries that
are not all-zero and strictly increase. Indexes of segments at or after the recovery point are
always rebuilt from the log. Timestamp lookup uses the largest entry with timestamp strictly less
than the target, then scans forward. This keeps the result exact when several batches share a
timestamp.

## D4. Time-based segment roll follows Kafka's `timeWaitedForRoll` (M1)

A non-empty active segment rolls when `incomingBatch.maxTimestamp - firstBatch.maxTimestamp >
segment.ms`, or, if the segment has no first-batch timestamp, when `now - segmentCreated >
segment.ms`. Producers that send timestamp 0 or replay old data therefore don't cause a roll on
every batch. Time-based retention compares each segment's largest timestamp with
`now - retention.ms` and, like size retention, deletes only a contiguous prefix of old segments.

## D5. Recovery requires contiguous offsets and canonical batches (M1)

During recovery, each batch's baseOffset must equal the previous batch's next offset. Each batch
must also pass full validation: CRC, canonical encoding and exact framing. The log is cut at the
first batch that fails, and later segments are deleted. Gaps can't happen legitimately, since
there is no compaction and retention only removes whole leading segments. Recovery never applies
`max.message.bytes`, because the value may have been lowered after the data was written.

## D6. Storage I/O methods take a context (M1)

Exported storage methods that do I/O take `ctx` first, per the coding conventions, and return
`ctx.Err()` before starting work. File I/O itself can't be interrupted.

## D7. Delayed deletion without reader refcounts; sticky I/O failure (M1)

Deleted segments are renamed `.deleted`, then closed and unlinked after `file.delete.delay.ms`.
Reads are short, so a 60 s delay is enough without refcounting (Kafka makes the same choice).
A reader that still hits a closed segment gets `ErrOffsetOutOfRange`, or `ErrClosed` if the
whole log was closed. It never crashes, because index lookups hold the index RWMutex. If a write
rollback or an fsync fails, the log enters a failed state and returns `ErrLogFailed` until it is
reopened. Linux may drop dirty pages after a failed fsync, so continuing could advance the
recovery point past lost data.

## D8. File modes and gosec G304 (M1)

Storage creates files with mode 0640 and directories with 0750, which satisfies gosec G301/G306.
G304 (file path from a variable) is excluded for `internal/storage/` only: every path there is
built from the configured data directory (from M2 also `internal/config/`, `internal/metadata/local/`,
`internal/broker/` and `test/`). In `_test.go` files, `contextcheck` (test helpers use
`context.Background()`), `unparam` (test helpers often take fixed arguments) and gosec G404 (math/rand for workload generation) are excluded.

## D9. Negative batch timestamps are rejected; trusted corruption keeps the log offline (M1)

`Log.Append` rejects a batch whose maxTimestamp is negative (`ErrInvalidTimestamp`). Time-based
retention and rolling compare segment timestamps against the wall clock, so a segment of
timestamp -1 batches would be deleted on the next retention pass after it rolled. Kafka handles
`NO_TIMESTAMP` with append-time fallbacks; streamq clients always set CreateTime, so it rejects
the batch instead. Recovery never truncates data below the recovery point, since that data was
fsynced and may be acknowledged. If such a segment is damaged (a partial batch, or an offset gap
to the next segment), `openLog` fails with `ErrCorruptLog` and changes nothing, rather than
deleting every newer segment to repair the log. Only segments that may hold unflushed data are
truncated, together with any later segments.

## D10. Proto naming exceptions (M2)

buf `STANDARD` lint wants enum zero values to end in `_UNSPECIFIED`. `ErrorCode`'s zero value is
success (SPEC §7.3 `NONE`), so an unset code in proto3 must never read as a failure.
`ENUM_ZERO_VALUE_SUFFIX` is excepted in `buf.yaml`, and `ERROR_CODE_NONE = 0` stays. Other
enums still use `_UNSPECIFIED`. The service is `StreamQService`, not SPEC §7.1's `StreamQ`,
because buf requires the `Service` suffix. Enum values carry the `ERROR_CODE_` prefix required by
buf. The SPEC names are the suffixes.

## D11. `leader_epoch = -1` skips the epoch check (M2)

Produce, Fetch and ListOffsets accept `leader_epoch = -1` to mean "don't check", as in Kafka.
This is used by tools such as streamqctl that don't track epochs. Any other value is checked as in
D12.

## D12. Request epoch newer than the broker's → NOT_LEADER (M2)

A request epoch below the partition's current epoch gets `FENCED_LEADER_EPOCH` (SPEC §4.4). An
epoch above it means this broker's metadata is behind. Kafka would return UNKNOWN_LEADER_EPOCH,
which is not in §7.3, so streamq returns `NOT_LEADER`: the client refreshes metadata and
retries.

## D13. Extra error codes (M2)

Four codes were added beyond SPEC §7.3:
- `INVALID_CONFIG`: bad topic config overrides;
- `INVALID_TOPIC`: bad topic name;
- `INVALID_TIMESTAMP`: `storage.ErrInvalidTimestamp`, D9 (Kafka has the same code);
- `UNKNOWN`: unexpected server errors, logged at ERROR.

## D14. `internal/broker` package (M2)

`internal/broker` is a replica-manager layer. It owns the storage manager, the partitions, the
HW checkpoint and the metadata subscription, and implements produce, fetch long-poll and
list-offsets. This keeps `internal/server` to thin gRPC handlers, as CLAUDE.md requires. The
package is not in the CLAUDE.md layout list.

## D15. HW checkpoint and single-node HW (M2)

The broker writes `<data_dir>/replication-offset-checkpoint` every 5 s and on shutdown. When a
partition becomes leader, its HW starts at min(checkpoint, LEO). With ISR = {self} it advances to
LEO immediately, and again after every append. M6 replaces this with min LEO over the ISR.

## D16. SPEC §10 defaults kept; CreateTopic doesn't check min.insync against RF (M2)

The defaults stay RF 3 / min.insync 2. As in Kafka, CreateTopic does not reject
min.insync > RF; `acks=all` then fails with `NOT_ENOUGH_REPLICAS` at produce time, before any
append. Single-node setups use `deploy/single-node.yaml` (RF 1, min.insync 1), and tests set
both explicitly.

## D17. Topic IDs, `partition.metadata` and stray-dir cleanup (M2; on-disk addition approved by the plan-reviewer)

`CreateTopicCommand.topic_id` is 16 random bytes in hex, generated by the proposer. Each
partition dir holds `partition.metadata` (`version: 0`, `topic_id: <id>`), written atomically
before the log is created. At startup a partition dir is renamed to
`<dir>.<id|stray>.<rand>.delete` and removed in the background if:
- it is not in the metadata snapshot,
- it has no readable `partition.metadata`, or
- its topic_id differs from the snapshot's.

This follows Kafka's stray-log handling. Deleting a topic removes its recovery-point and HW
checkpoint entries before renaming the dir, so a recreated topic never inherits stale offsets.
These are new files only; the M1 segment, index and checkpoint formats are unchanged.

## D18. CreateTopic and DeleteTopic wait for local application (M2)

After `Propose`, the handler waits for the change to be applied locally. Create waits until every
local partition is open as leader; delete waits until they are removed. The wait is bounded by
the request deadline, or 30 s if there is none. So a produce right after create succeeds on the
broker that handled the create.
The CreateTopic handler validates everything that `Apply` and the partition open check
(`ResolveTopicConfig`, name, RF), so invalid input never reaches `Propose`. If opening a log still
fails after the command is committed (an I/O error), the topic stays in metadata, the handler
returns the error, and any partitions already opened keep serving. The operator deletes and
recreates the topic. This is Kafka's behaviour as well: topic creation is not transactional with
the logs.

## D19. Request limits (M2)

`max_wait_ms` is capped at 30 s and request `max_bytes` at 16 MiB. gRPC send and receive limits
are 64 MiB on server and client.

## D20. streamqctl stays on the generated gRPC stubs (M3)

The CLI is a thin, low-level tool. Its tests already cover the wire API directly, and moving it
onto `pkg/client` would mean rework for no functional gain. Applications use `pkg/client`.

## D21. At most one in-flight batch per partition before idempotence (M3)

Until M7 adds sequence numbers, the producer sends each partition's batches strictly one at a
time, retries included. A retried batch can then never land after a later batch of the same key
(Kafka's `max.in.flight.requests.per.connection=1` guarantee). FR3 holds under retries.

## D22. Client defaults (M3)

The defaults follow Kafka, except that linger is 5 ms (as in Kafka 4.0):
- acks=all, linger 5 ms, batch.size 16 KiB, buffer.memory 32 MiB;
- max request size 1 MiB, delivery timeout 2 min, max.block 60 s;
- retry backoff 100 ms → 1 s with full jitter, request timeout 30 s, metadata max age 5 min;
- consumer auto.offset.reset = latest, fetch max wait 500 ms.

## D23. Producing to an unknown topic waits for metadata (M3)

`Produce` refreshes metadata with backoff until the topic appears, bounded by the caller's ctx,
`ProducerConfig.MaxBlock` (60 s, Kafka `max.block.ms`) and producer close. After that it returns
`ErrUnknownTopicOrPartition` (or `ErrProducerClosed`) synchronously.

## D24. MESSAGE_TOO_LARGE splits the batch (M3)

The producer seals batches at `min(BatchSize, MaxRequestSize, topic max_message_bytes when
known)`. The topic limit is not always visible to the client, so if the broker still rejects a
multi-record batch with `MESSAGE_TOO_LARGE`, the producer splits it in half and puts both halves
back at the head of the partition queue (Kafka's `splitAndReenqueue`), recursing as needed. Order
is preserved because only one batch is in flight. Only a single-record batch fails with
`ErrMessageTooLarge`.

## D25. Consumer group protocol: server-side assignment with Kafka's state machine (M4)

The coordinator computes assignments (SPEC §5) using range or round-robin. The chosen assignor is
the first one in the earliest-joined member's list that every member supports. Group states:
- Empty;
- PreparingRebalance: completes when every member has rejoined, or at the rebalance timeout.
  Members parked in Join are kept alive; other members still expire;
- Stable.

Completion is atomic under the coordinator lock, so there is no CompletingRebalance state.
Commits from the current generation are accepted in PreparingRebalance and Stable (Kafka). A new
group waits `group_initial_rebalance_delay_ms` (new key, default 3 s, Kafka's
`group.initial.rebalance.delay.ms`), restarted per joiner but capped by the rebalance timeout.
`group_session_timeout_ms` is the default and maximum session timeout: larger requests are
clamped rather than rejected, because §7.3 has no INVALID_SESSION_TIMEOUT.
`group_rebalance_timeout_ms` is the default rebalance timeout. The PreparingRebalance cap is fixed
when the phase starts, from the members present then. A later joiner with a larger rebalance
timeout does not extend it, which is simpler than Kafka's max over current members; members still
rejoin in the next round. Topic creation or deletion for a
subscribed topic triggers a rebalance. A Join abandoned by its client removes a member that the
same request created.

## D26. Standalone commits only for groups without members (M4)

A commit with generation -1 and no member id is accepted only when the group has no members, as
in Kafka. Otherwise it gets UNKNOWN_MEMBER_ID.

## D27. Deleting a topic deletes its committed offsets (M4)

`DeleteTopic` removes the topic's committed offsets from every group, and drops groups left with
no offsets. A recreated topic never resumes from stale offsets.

## D28. `metadata.json` gains `groups` (M4; additive on-disk change, approved by the plan-reviewer)

The local store persists committed offsets as `groups: {group: {topic: {"partition": offset}}}`.
Older files without the key load with no offsets. Negative offsets are rejected on load.

## D29. Extra group RPCs and per-partition commit results (M4)

`ListGroups` and `DescribeGroup` go beyond SPEC §7.1; they back `streamqctl groups list`,
`describe` and `lag` (FR11). `CommitOffsetResponse.results` reports per-partition errors (Kafka
shape), so a deleted topic does not fail the commits of other partitions. Empty group ids and
unknown or no common assignors are invalid requests (gRPC InvalidArgument). A stopped coordinator
answers NOT_COORDINATOR.

## D30. Two metadata modes, no migration (M5)

Single-node mode (empty `cluster`) keeps the local JSON store (`metadata.json`). Cluster mode uses
the Raft store (`<data_dir>/raft/`). A data dir is never migrated between modes. Starting with the
other mode's metadata present fails fast, so partition directories are never misclassified as
stray.

## D31. Internal gRPC service on `internal_addr` (M5)

`StreamQInternalService` (RegisterBroker, BrokerHeartbeat, ForwardMetadata; replication RPCs in
M6) is a separate gRPC server on `internal_addr`, apart from the client API. Raft uses its own
TCP transport on `raft_addr`.

## D32. Raft timing knobs (M5)

Optional config keys `raft_heartbeat_timeout_ms` and `raft_election_timeout_ms` (default 1000) and
`raft_snapshot_threshold` (default 8192). Validation requires election ≥ heartbeat timeout. Tests
use 300 ms.

## D33. Forwarding and leader-only writes (M5)

A follower forwards CreateTopic/DeleteTopic proposals to the controller (KIP-590-like) and waits
until it has applied the resulting index locally, so `Store.Propose` means "applied here". It
retries only when the entry certainly was not appended (not leader before Apply, dial failure, no
leader known). Unknown outcomes such as leadership lost mid-apply or a deadline are returned. A
client-level CreateTopic retry after an unknown outcome can therefore report TOPIC_ALREADY_EXISTS
for a create that succeeded (as in Kafka); Admin treats that as success after a transport error
when the partition count matches. Controller commands and group offset commits are leader-only
(`ProposeAsLeader`). They carry the Raft term their issuer activated in (`controller_epoch`), and
the FSM rejects them if they commit in another term. A deposed controller or coordinator can never
write. DeleteTopic carries the topic id it validated, so a retried delete never removes a recreated
topic. An unknown outcome (leadership lost mid-commit, apply timeout) is reported as
REQUEST_TIMED_OUT.

## D34. Fencing semantics (M5)

Fencing removes the broker from every ISR except as the last member, so unclean election stays
impossible. Partitions it led elect the first unfenced ISR member in replica order (leader
epoch++), or go offline (leader -1). Unfencing re-elects offline partitions whose ISR contains the
broker. Fence and unfence carry the broker epoch and are no-ops for another incarnation, or when
the broker is already in the target state.

## D35. Registration and catch-up (M5)

`RegisterBroker` (re-)registers a broker fenced, with partition effects identical to fencing, and
bumps its epoch. The broker opens its partitions only after its FSM has applied up to the
registration entry's index. The controller unfences it once its heartbeat reports a processed
metadata index at or beyond that index.

## D36. Replication factor counts unfenced brokers (M5)

CreateTopic requires RF ≤ the number of unfenced registered brokers (Kafka's usable brokers)
rather than all registered ones. New partitions start with ISR = the unfenced replicas.

## D37. On-disk additions and go-hclog (M5; approved by the plan-reviewer)

Broker records gain `internal_addr`, `fenced` and `epoch` (optional JSON keys). The Raft FSM
snapshot is JSON `{"version": 1, "state": {...}}`, and Restore rejects unknown versions. Raft data
lives in `<data_dir>/raft/` (bolt log/stable store, file snapshots). `github.com/hashicorp/go-hclog`
is imported directly: it is hashicorp/raft's logger interface, already in the module graph, and
the slog adapter needs it.

## D38. `STALE_BROKER_EPOCH` error code (M5)

Code 22, internal API only, Kafka's name. A heartbeat from an old broker incarnation gets it, and
the broker re-registers.

## D39. Follower truncation deletes segments immediately (M6)

`Log.TruncateTo` deletes segments wholly at or after the cut immediately (newest-first, with a
dir fsync after each), then cuts the containing segment at a batch boundary. Only followers
truncate, and followers serve no consumer reads. The caller then synchronously rewrites the
recovery-point checkpoint before appending again. A replica fetch from a just-demoted leader racing
its truncation can return data that is then truncated. That is harmless: the fetching follower
re-truncates against the new leader through OffsetForLeaderEpoch.

## D40. High watermark rules (M6)

The leader's HW is the min LEO over the maximal ISR (D45) and never decreases while it remains
leader. A follower's HW is min(leader HW, own LEO). A follower lowers its HW only when truncating
below it, so a later leader never exposes truncated data (FR4).

## D41. ISR expansion rule (M6)

A follower joins the ISR when its LEO ≥ the HW and ≥ the start offset of the leader's current
epoch (KIP-841), and it is not fenced in the leader's metadata. Kafka's caught-up rule drives
shrinking: a follower is caught up at fetch time if it fetched from the current LEO, or as of its
previous fetch if it reached the LEO observed then. It is removed after `replica_lag_max_ms`
without catching up.

## D42. Replication concurrency model (M6)

There is one fetcher goroutine per followed partition, owned and joined by the broker, and one RPC
per partition (no per-broker batching). Fetchers exit only on cancellation and back off on errors.
AlterISR requests are sent by one broker-wide ISR loop, at most one in flight per partition.

## D43. acks=all purgatory (M6)

An acks=all produce waits on the gRPC handler goroutine, using the partition's HW and
leadership-change channels with an injected-clock timeout. It succeeds only if the replica is still
leader in the epoch the batch was appended in, and the HW has passed the batch. The default wait is
`timeout_ms` (30 s if 0), capped just below the RPC deadline.

## D44. NOT_ENOUGH_REPLICAS after append (M6)

When the HW passes an acks=all batch but the committed ISR has dropped below min.insync, the
produce returns NOT_ENOUGH_REPLICAS (retriable; the data may still commit). Kafka's
NOT_ENOUGH_REPLICAS_AFTER_APPEND maps to this §7.3 code.

## D45. Maximal ISR (M6, KIP-497)

The leader computes the HW over committed ISR ∪ pending AlterISR additions, and keeps counting
members a pending shrink would remove. min.insync uses the committed ISR. Pending state is cleared
only when newer partition metadata arrives, or when the controller rejects the ISR content at
matching epochs. A FENCED reply keeps it, which freezes ISR changes for that partition until its
metadata catches up (as in Kafka). That is the safe direction: the HW stalls rather than acking
under-replicated data. Transport errors retry the same request.

## D46. KIP-279 follower truncation (M6)

A follower asks the leader for the end offset of its latest epoch and truncates to
min(LEO, leader end). If the leader knows only an older epoch E', it also truncates to its own end
of E' and repeats. Without epoch information on either side it truncates to its HW. Below the
leader's log start it restarts empty at that offset.

Refinements from the M6 review:
- If the follower also has E', both logs agree up to min(LEO, leader end, own end of E'). It
  truncates there, drops any later (possibly empty) local epochs, and stops.
- It iterates only when it lacks E'. That intermediate step also clamps to the leader's end. This
  truncates at most what is already divergent, so it is slightly more than Kafka but safe.
- A stale empty epoch can never block progress: epoch entries at or after the new LEO are always
  dropped, and `Assign` replaces any entry at the same start offset.
- Truncation writes the recovery-point and HW checkpoints synchronously before the next append.

## D47. `INVALID_ISR` internal error code (M6)

Code 23, internal API only. AlterISR content rejections (members that are not replicas, the leader
missing, fenced members) are distinguished from FENCED_LEADER_EPOCH, because the leader clears
its pending state only for the former.

## D48. Client idempotence (M7)

Idempotence is on when `Acks == AcksAll` and `DisableIdempotence` is false, which matches Kafka
≥ 3.0's default.
- **Producer ID:** obtained lazily via `InitProducer`. The producer epoch stays 0 (SPEC §3.5).
- **Sequences:** a batch gets its sequence on its first send attempt and keeps it across retries.
  One batch is in flight per partition (D21), which satisfies "≤ 5 in flight".
- **Unknown outcome:** after a sequenced batch finally fails (timeout, OUT_OF_ORDER_SEQUENCE,
  UNKNOWN_PRODUCER_ID, …), the producer obtains a new producer ID before the next sequence
  assignment. This replaces Kafka's epoch bump.
- **Reordering:** without epoch fencing, a timed-out batch still in flight on the server may land
  after later batches. This is acceptable, because the application was already told it failed.
- **Throughput:** one batch in flight per partition limits throughput; M10 measures it.
- **Existing tests edited in M7 (none weakened):**
  - `pkg/client/fake_test.go`: the fake gained InitProducer and (tp, pid, seq) dedup, and its
    default Produce moved into `produce()`.
  - `internal/metadata/state_test.go`: isolation checks were extended to the producer-ID fields.
  - `raftstore/store_test.go`: the snapshot round trip applies one more command, so the expected
    index went from 4 to 5.
  - `pkg/client/admin_test.go`: a pre-existing data race on a call counter was fixed with an
    atomic.

## D49. Producer-state eviction (M7)

- **Eviction:** producers are evicted only after `producer_id_expiration_ms`, measured on the
  batch max timestamp. The timestamp is deterministic on replay. There is no eviction when the
  log start moves.
- **Unknown producers:** an unknown producer with sequence ≠ 0 gets UNKNOWN_PRODUCER_ID, which is
  non-retriable for the batch; the client re-initializes.
- **Known state-loss cases (Kafka-like):**
  - a full truncation (`TruncateFullyAndStartAt`) on a follower that is later promoted;
  - a missing roll snapshot at the log start after retention.

  Producers whose batches survive only in deleted segments then get UNKNOWN_PRODUCER_ID.
- **Expiry uses client timestamps (Kafka parity):** expiry is measured on batch CreateTime. A
  producer backfilling old timestamps, or with a clock days behind, can expire right after an
  append. Its next batch then gets UNKNOWN_PRODUCER_ID and the client re-initializes. A clock
  running ahead keeps the entry until the timestamp passes.
- **Size limit before dedup:** validation, including `max_message_bytes`, runs before the dedup
  check (M7 plan R3). If a topic's `max_message_bytes` is lowered between a lost-response attempt
  and its retry, the retry gets MESSAGE_TOO_LARGE although the batch is in the log. The client
  then splits it and the halves fail with OUT_OF_ORDER_SEQUENCE. This is reported to the
  application, and data is never silently lost.

## D50. Producer-state snapshots (M7)

- **Format:** `<20-digit offset>.snapshot` holds a 4-byte CRC32C followed by a JSON body. It covers
  every batch with last offset < offset.
- **When written:** synchronously on segment roll, and at the LEO on clean shutdown. A failed write
  is logged and is not fatal.
- **Rebuild:**
  1. Delete snapshots outside [log start, LEO], corrupt snapshots and temp files.
  2. Load the newest valid snapshot.
  3. Replay the later batch headers.
  4. Swap the result in only on success.
- **Failed rebuild:** the producer state is marked invalid. Idempotent appends then get NOT_LEADER
  until a retry succeeds.
- **Full truncation:** deletes snapshots before the log.

## D51. Producer-ID blocks (M7)

- **Allocation:** the controller allocates blocks of 1000 through `AllocateProducerIDsCommand`.
  The FSM keeps `next_producer_id` and `producer_id_blocks[broker]`.
- **Result:** the controller reads the result after applying, under `allocMu`, and re-checks its
  term (M7 plan R13).
- **Single-node mode:** proposes to the local store under the broker allocator's mutex.
- **On disk:** `metadata.json` and the Raft snapshot gain the two keys (additive). Older files load
  as 0 and empty.
- **Lost responses:** IDs lost to lost responses are wasted, never reused.

## D54. Compose topology and shutdown budget (M8)

- **Broker-to-broker traffic:** internal and Raft traffic in `deploy/docker-compose.yml` goes
  through toxiproxy, so M9 can inject faults.
- **Client traffic:** direct. Broker N listens on and publishes 9092/9192/9292, advertised as
  `localhost`. Clients inside the compose network are unsupported.
- **Shutdown budget:** `controlled_shutdown_timeout_ms` defaults to 30000. The compose configs use
  10000 so rolling restarts stay quick, with `stop_grace_period: 30s`: the 10 s controlled budget,
  10 s graceful drain, and a margin.
- **`cluster status`:** lists live brokers only, as Kafka's describeCluster does. Brokers that are
  referenced as replicas but absent are shown as "down".

## D52. Metrics (M8)

- **Registry:** one `metrics.Metrics` per node, with its own registry (no globals).
- **Names:** as in `docs/plans/M8.md` §1.
- **Labels:**
  - `code` on `streamq_requests_total` is the gRPC status. Per-partition API errors are counted in
    `streamq_partition_errors_total{method,error_code}`.
  - `streamq_partitions_offline` is exported by the controller (or single-node) only.
  - Consumer lag and the ISR gauges are exported by partition leaders.
  - Raft last-contact is 0 on the leader.
- **Buckets:** latency buckets run from 0.5 ms to 60 s, to cover 30 s long-polls.
- **Dependency:** `github.com/prometheus/common` (expfmt/model) is used directly by the metrics
  tests. It comes from the same project as the approved client_golang, was approved by the M8
  plan-reviewer, and was already transitive.
